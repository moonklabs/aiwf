# ADR 설계 결정 기록 형식

> 휴먼 리뷰용 한글 번역입니다. 실행 원문: [원문 스냅샷](source/ADR-FORMAT.md). 번역과 자동 검사는 승인을 뜻하지 않으며, 검토 상태와 원문 SHA256은 [관리 목록](../../manifest.json)에서 확인합니다.

ADR은 `docs/adr/`에 두고 `0001-slug.md`, `0002-slug.md`처럼 순서대로 번호를 붙인다. 기본 경로는 `docs/adr/`이며 첫 ADR이 필요할 때만 디렉터리를 만든다. 이 로컬 규약은 저장소 core의 `docs/architecture/` ADR 규약과 경로가 다르므로 해당 저장소에서 따를 규칙을 별도로 확인한다.

## 템플릿

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

짧은 결정 제목과 맥락·결정·이유를 담은 1~3문장이 전부다. ADR은 한 문단이어도 된다. 항목을 채우는 것보다 결정이 내려졌다는 사실과 그 이유를 기록하는 데 가치가 있다.

## 선택 항목

실제 도움이 될 때만 추가한다. 대부분의 ADR에는 필요하지 않다.

- **Status** frontmatter: `proposed | accepted | deprecated | superseded by ADR-NNNN`. 결정을 다시 검토할 때 유용하다.
- **Considered Options:** 거절한 대안을 기억할 가치가 있을 때만 사용한다.
- **Consequences:** 자명하지 않은 후속 영향을 드러내야 할 때만 사용한다.

## 번호 매기기

`docs/adr/`의 기존 최대 번호를 확인하고 1을 더한다. 경로·번호 규칙을 확인할 때는 이 상대 경로를 기준으로 한다.

## ADR을 제안할 조건

다음 세 조건을 모두 만족해야 한다.

1. **되돌리기 어렵다.** 나중에 결정을 바꾸는 비용이 상당하다.
2. **맥락 없이는 의외로 보인다.** 미래 독자가 코드를 보고 “대체 왜 이렇게 했지?”라고 생각할 수 있다.
3. **실제 대안 사이에서 선택했다.** 현실적인 대안들이 있었으며 구체적 이유로 하나를 선택했다.

쉽게 되돌릴 결정이면 생략한다. 의외가 아니라면 누구도 이유를 궁금해하지 않는다. 실제 대안이 없었다면 자명한 선택을 했다는 사실 외에 기록할 것이 없다.

### 기록할 만한 결정

- **아키텍처 구조:** 모노레포 사용, 쓰기 모델의 이벤트 소싱과 읽기 모델의 Postgres 투영 같은 결정.
- **컨텍스트 사이의 연동 패턴:** Ordering과 Billing이 동기 HTTP 대신 도메인 이벤트로 통신한다는 결정.
- **교체 비용이 큰 기술 선택:** 데이터베이스, 메시지 버스, 인증 공급자, 배포 대상. 모든 라이브러리가 아니라 교체에 한 분기가 걸릴 정도의 선택이다.
- **경계와 범위 결정:** 고객 데이터는 Customer 컨텍스트가 소유하고 다른 컨텍스트는 ID로만 참조한다는 결정. 하지 않기로 한 것도 하기로 한 것만큼 중요하다.
- **자명한 경로에서 의도적으로 벗어난 선택:** 특정 이유로 ORM 대신 수동 SQL을 쓰는 경우처럼, 독자가 반대를 예상할 만한 결정. 후속 개발자가 의도된 선택을 잘못 고치는 일을 막는다.
- **코드에 드러나지 않는 제약:** 규정 준수 때문에 AWS를 사용할 수 없거나 파트너 API 계약으로 응답 시간이 200ms 미만이어야 하는 경우.
- **거절 이유가 자명하지 않은 대안:** 미묘한 이유로 GraphQL 대신 REST를 선택했다면 기록한다. 그렇지 않으면 6개월 후 다시 같은 대안이 제안될 수 있다.
