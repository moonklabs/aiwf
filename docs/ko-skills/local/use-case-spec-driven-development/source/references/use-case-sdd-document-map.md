# 유스케이스 중심 SDD 문서 맵

이 문서 구조는 요구사항을 유스케이스로 구체화하고 설계·테스트·작업분해·구현 사이의 연결을 유지하기 위한 실용적인 프로젝트 규약이다. 공식 표준이나 특정 프레임워크의 인증 방법론을 뜻하지 않는다. 저장소의 관행, 프로젝트 규모, 사용자의 산출물 요청에 맞춰 선택한다.

Use Case는 화면이나 버튼이 아니라 사용자가 달성하려는 하나의 응집된 목표를 표현한다. 단순 CRUD 구성요소는 상위 목표 아래 묶을 수 있다. 업무에 불필요한 문서는 만들지 않는다.

## 유스케이스 상세 작성 기준

각 유스케이스에는 다음 중 프로젝트에 필요한 항목을 둔다.

- `UC-NNN`, 이름, 목적, 우선순위, 상태
- 주 액터와 지원 시스템
- 시작 조건/트리거, 사전조건, 성공 보장과 최소 보장
- 번호가 있는 기본 흐름: 액터 행동과 시스템 응답을 구분
- 근거가 있는 대안 흐름과 예외/실패 경로
- 관련 FR/NFR/BR/TC/WP
- 비기능 제약, 권한/감사/데이터 영향 등 특별 요구사항
- 기존 시스템이면 코드·테스트·스키마 근거와 신뢰도. 신규 시스템이면 승인된 결정, 가정, 검토 질문

흐름은 테스트 가능한 결과를 만들도록 구체적으로 쓴다. 내부 클래스 호출 순서를 사용자 목표 흐름으로 오인하지 않는다. 대안 경로가 확인되지 않았으면 상상으로 채우지 말고 미정으로 표시한다.

## 테스트와 작업분해

TC는 Use Case 기본 흐름뿐 아니라 중요한 대안·권한 거부·검증 실패·경계 조건에서 파생한다. 각 TC에 단위/통합/API/UI/수동 중 적절한 검증 수준, 관찰 가능한 기대 결과, 자동화 상태를 적는다. 이미 존재하는 테스트, 새로 작성할 테스트, 아직 실행하지 않은 검증을 분명히 구분한다.

WP는 UC 결과를 중심으로 세로로 나눈다. 각 WP는 가능하면 UI/API/도메인/데이터/검증을 연결해 독립적으로 시연·검토 가능한 결과를 내야 한다. 필요한 기반 작업과 레이어별 선행조건은 둘 수 있지만, 파일 목록만 나열한 작업계획으로 끝내지 않는다. 작업마다 관련 ID, 완료 정의, 테스트, 의존성, 위험, 미포함 범위를 둔다.

권장 상태는 `초안`, `검토 필요`, `승인`, `진행 중`, `검증 완료`, `보류`다. 프로젝트가 다른 상태 체계를 쓰면 기존 용어를 따른다. 테스트 통과 상태는 실제 실행한 검증만 표시한다.

## 아키텍처 문서

복잡성에 맞게 선택적으로 `docs/architecture/README.md`와 다음 관점을 유지한다.

| 경로 | 관점 |
| --- | --- |
| `logical.md` | 모듈 책임, 시스템 경계, 의존 관계 |
| `process.md` | 핵심 유스케이스의 요청·권한·상태 전이 순서 |
| `development.md` | 개발환경, 빌드·테스트 명령, 검증 제약 |
| `physical.md` | 확인된 배포/런타임 구성과 설정 경계. 비밀정보는 기록하지 않음 |
| `scenarios.md` | 시스템·액터·외부 연동을 가로지르는 주요 시나리오 |
| `decisions/ADR-NNN-*.md` | 중요한 기존 또는 제안 설계 결정, 상태, 대안과 결과 |

ADR은 현재 시스템에서 근거가 확인된 결정을 기록하거나 신규 설계에서 실제 선택이 필요한 결정을 제시한다. 결정이 확인되지 않았는데 선택을 이미 끝난 사실처럼 쓰지 않는다. 데이터베이스 경계, 권한 모델, 통합 방식, 마이그레이션 등 장기 영향이 큰 결정에 우선 사용한다.

## 모드별 기록 규칙

### 신규 개발

- `To-Be` 목표 요구사항과 현행 제약을 구분한다.
- 사용자에게서 확인한 결정, 임시 가정, 열려 있는 결정을 구별한다.
- 먼저 요구사항·유스케이스·도메인·아키텍처 제약·인수 기준의 연결을 만들고, 그 연결을 바탕으로 WP와 테스트를 도출한다.
- 합의된 범위라면 문서 작성 후 구현으로 이어가고, 실제 변경과 검증 결과로 문서를 갱신한다.

### 기존 시스템 역공학

- `As-Is` 구현 사실, 테스트 보장, 추론, 확인 필요 항목을 분리한다.
- 화면/라우트 목록을 API, 권한, 데이터, 테스트와 연결한다. 범위가 크면 전체 인벤토리와 상세 분석 완료 범위를 각각 표시한다.
- 개선 제안이나 목표 상태는 현행 요구사항처럼 쓰지 말고 별도 `To-Be` 또는 제안 절에 둔다.
- 별도 요청이 없으면 문서만 변경하며 소스 코드나 스키마를 고치지 않는다.

### 기존 시스템 확장

- 변경 대상 UC의 현재 흐름과 영향 받는 연동/데이터/권한을 먼저 확인한다.
- 신규/변경 FR과 UC를 기존 계약 및 ID에 연결한다. 삭제·호환성·데이터 이전 영향을 명시한다.
- 구현 후 실제 변경된 계약·흐름·테스트 결과를 동기화한다.

## 문서 품질 및 추적성 체크

- `README.md`에서 유지하는 모든 문서로 연결되며 깨진 상대경로가 없다.
- 각 FR/NFR은 근거나 결정 상태가 있고 관련 목표/UC와 연결되어 있다.
- 주요 UC는 관련 BR/TC를 연결하고, 구현 시에는 WP와 검증 결과까지 추적된다.
- 엔티티, 흐름도, 아키텍처 서술, 코드/스키마가 서로 모순되지 않는다.
- `As-Is`, `To-Be`, 가정, 제안, 미확정 결정의 상태가 혼재되지 않는다.
- 구현 증거, 테스트 존재, 테스트 통과, 제안된 TC를 서로 바꾸어 말하지 않는다.
- 범위 밖이거나 상세 분석되지 않은 영역과 그 이유를 기록한다.
