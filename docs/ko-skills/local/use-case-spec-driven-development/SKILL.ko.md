# 유스케이스 중심 명세 기반 개발

> 휴먼 리뷰용 한글 번역입니다. 실행 원문: [원문 스냅샷](source/SKILL.source.md). 번역과 자동 검사는 승인을 뜻하지 않으며, 검토 상태와 원문 SHA256은 [관리 목록](../../manifest.json)에서 확인합니다.

**식별자:** `use-case-spec-driven-development`  
**설명:** 유스케이스 중심 명세, 추적 가능한 요구사항, 인수 테스트, 아키텍처 결정과 구현 작업 패키지로 소프트웨어를 계획하고 완성한다. 기존 시스템을 같은 모델로 역공학하는 데도 사용한다. 이해관계자의 목표를 실행·검증 가능한 소프트웨어로 연결해야 할 때 사용한다.

사용자 목표와 유스케이스를 요구사항에서 설계, 테스트, 작업분해와 코드로 이어지는 연결로 삼는다. 이 문서 모음은 실용적인 프로젝트 규약이며 공식 방법론이나 표준 준수를 주장하지 않는다.

## 모드를 선택한다

- **새 시스템 / 새 기능:** 목표인 `To-Be` 동작을 정하고 명세화한다. 유스케이스 중심으로 사용자 결과를 끝까지 연결하는 작업 패키지로 나눈 뒤 구현·테스트하고 결과와 명세를 동기화한다.
- **기존 시스템 분석:** 저장소 근거로 현재 `As-Is` 동작을 재구성하고 추적 가능한 문서를 만든다. 구현이 별도 요청되지 않았으면 애플리케이션 동작을 변경하지 않는다.
- **기존 시스템 확장:** 관련 현재 동작을 먼저 문서화한 뒤 제안하는 변경을 별도로 명세화한다. 기존 제약을 보존하고 마이그레이션이나 호환성 영향을 표시한다. 기존 계약을 묵시적으로 재정의하지 않는다.

분석, 계획 또는 문서만 요청되었다면 해당 산출물에서 멈춘다. 개발이나 구현을 요청했다면 명세 작성에서 멈추지 않고 승인되었거나 경계가 명확한 요구사항을 코드와 검증까지 이어 간다.

## 원칙

- 사용자가 다른 언어를 요청하지 않으면 산출물은 기본적으로 한국어로 작성한다.
- 적용되는 `AGENTS.md`, 저장소 문서, 코드, 테스트와 관행을 먼저 읽는다. 기존 프로젝트 용어와 문서 경로를 사용한다. 없다면 `docs/`를 사용하고 [문서 맵 한글 검토본](references/use-case-sdd-document-map.ko.md) / [원문](source/references/use-case-sdd-document-map.md)을 조정한다.
- 사용자·업무 목표는 의도이며 현행 동작의 증거가 아니다. 현재 구현, 목표 요구사항, 설계 결정, 가정과 열린 질문을 구분한다.
- 현행 상태는 소스, 스키마, 설정, 런타임 관찰 또는 테스트에 근거를 둔다. 목표 상태는 명시적 사용자 입력에 근거를 두거나 검토할 가정으로 표시한다.
- 미해결 결정이 범위, 사용자에게 보이는 동작, 데이터·보안 경계, 호환성이나 수용 기준을 실질적으로 바꿀 때만 구체적으로 질문한다. 무엇을 검토해야 하는지, 근거만으로 결정할 수 없는 이유와 영향을 명시한다. 위험이 낮은 가정을 분명히 밝히고 되돌릴 수 있는 작업을 계속한다.
- 문서를 과도하게 만들지 않는다. 이해를 공유하는 데 도움이 될 때 참조 구조를 사용한다. 무관한 산출물은 생략하고 중요한 범위 공백을 설명한다.

## 진행 절차

1. **목표와 경계를 이해한다.** 사용자·액터, 문제, 결과, 범위 안팎의 동작, 기존 제약, 영향을 받는 시스템과 요청된 종료 지점인 분석·명세·계획·구현을 확인한다. 편집 전에 저장소 지침과 상태를 조사한다.
2. **근거를 찾고 구분한다.** 기존 시스템에서는 라우트·진입점을 UI, API·서비스, 권한, 저장 데이터, 연동·작업, 설정과 테스트에 연결한다. 오래된 문서보다 현재 실행 동작과 테스트를 우선하고 충돌과 미확인 사항을 기록한다. 신규 개발에서는 이해관계자의 의도를 담고 확정된 결정과 가정을 구분한다.
3. **액터 목표와 요구사항을 명세화한다.** 화면이나 버튼마다 하나씩 나누지 않고 응집된 유스케이스를 정의한다. 기능 요구사항, 업무 규칙, 품질 요구사항, 도메인 개념과 관찰 가능한 인수 기준을 도출한다. `As-Is`와 `To-Be`를 분리한다. 안정적인 ID로 요구사항과 이를 뒷받침하는 유스케이스를 연결한다.
4. **설계와 테스트 전략을 정한다.** 책임, 경계, 중요한 흐름, 데이터 소유권, 연동과 영향이 큰 결정을 설명하는 데 필요한 아키텍처만 기술한다. UC의 기본·대안·실패 흐름에서 테스트 시나리오를 도출한다. 테스트 수준과 근거를 명시한다. 기존 자동화 테스트와 제안된 테스트를 구분하고 실행하지 않은 검증을 완료로 보고하지 않는다.
5. **사용자 가치로 구현 작업을 나눈다.** 구현 범위를 UC 결과를 처음부터 끝까지 제공하고 검증하는 순서 있는 작업 패키지 `WP`로 나눈다. 각 패키지는 관련 `FR`/`UC`/`TC` ID, 동작과 경계, 의존성, 인수 검사와 종료 기준을 명시하며 검토 가능해야 한다. 필요한 기술 기반 작업은 두되 파일·모듈별 할 일만 나열한 계획을 피한다. 순서, 통합, 데이터 이전과 위험을 드러낸다.
6. **구현하고 계약을 맞춘다.** 저장소 패턴과 명시적 범위를 따른다. 작은 단위로 개발하고 가장 관련 있는 검사를 실행하며 실패를 증거와 함께 보고한다. 실제 동작·설계가 명세와 다르면 코드를 맞추거나 명세 변경을 투명하게 기록해 모순을 남기지 않는다. 중요한 영향이 있는 결정에는 검토를 요청하되 일상적인 가역 작업에 확인을 요구하지 않는다.
7. **추적성을 검증하고 보고한다.** 링크, ID, 필요할 때 라우트·기능 범위, 다이어그램 일치, 인수 기준과 테스트 대응, 패키지 완료를 확인한다. 생성·변경 산출물, 구현 범위, 검사와 결과, 미해결 검토 결정과 미검증 사항을 보고한다.

## 추적성과 신뢰도

연결을 실용적이고 찾아갈 수 있게 유지한다.

`목표 -> 요구사항(FR/NFR) -> 유스케이스(UC) -> 업무 규칙(BR) / 테스트(TC) -> 작업 패키지(WP) -> 구현 근거`

기존 시스템 조사에는 도움이 될 때 다음 근거 표시를 사용한다.

- `구현 확인`: 코드나 런타임 동작에서 직접 확인했다.
- `테스트 확인`: 조사하거나 실행한 테스트가 보장하며 어떤 테스트인지 명시한다.
- `설정/스키마 확인`: 스키마, 라우트, 권한 또는 설정으로 정의되어 있다.
- `추론`: 근거가 있는 해석이지만 직접 명세화되어 있지 않다.
- `확인 필요`: 모호함, 누락, 낡은 정보, 충돌 또는 이해관계자 결정 대기 상태다.

모든 요구사항마다 별도 파일이나 자동화 테스트가 필요한 것은 아니다. 템플릿을 채우려고 빈 산출물을 만들거나 근거 링크를 조작하거나 제안된 인수 검사를 통과로 표시하지 않는다. 생성한 문서에서 자격 증명과 개인정보를 보호한다.
