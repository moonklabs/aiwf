# 유스케이스 명세 (Use Case Specification)

> 휴먼 리뷰용 한글 번역입니다. 실행 원문: [원문](../../../../../plugins/aiwf-core/skills/use-case-spec/SKILL.md). 번역과 자동 검사는 승인을 뜻하지 않으며, 검토 상태와 원문 SHA256은 [관리 목록](../../../manifest.json)에서 확인합니다.

- 스킬 식별자(name): `use-case-spec`
- 설명(description): 액터, 사전 조건, 주 성공 시나리오, 대안 흐름, 사후 조건, 비즈니스 규칙을 포함한 상세 유스케이스 명세 문서를 만든다. 사용자가 "유스케이스를 작성", "유스케이스를 명세", "시스템 동작을 문서화", "시나리오를 정의", "기능 명세를 작성"을 요청하거나 유스케이스 명세, 인수 기준, 사용자 시나리오를 언급할 때 사용한다. 또한 유스케이스 다이어그램(예: `docs/use_cases.puml`)에 있는 유스케이스에 대한 명세 문서를 작성하는 작업이면 언제든 트리거한다. "코드를 작성하기 전에 상세 유스케이스 명세", "유스케이스마다 한 파일" 같은 표현이나, 각 유스케이스의 해피 패스, 대안 흐름, 사후 조건, 비즈니스 규칙을 다루라는 요청을 포함한다.

## 지침

`docs/use_cases/`에 $ARGUMENTS에 대한 유스케이스 명세 문서를 만들거나 갱신한다. 각 유스케이스는 액터와 시스템이 하나의 목표를 달성하기 위해 수행하는 완전한 상호작용을 설명한다.

## 파일 이름 규칙 (정확히 이대로 수행)

유스케이스마다 파일 하나를 `docs/use_cases/UC-XXX-<kebab-case-name>.md`에 작성한다. 여기서:

- `UC-XXX`는 유스케이스의 세 자리 ID다(예: `UC-001`).
- `<kebab-case-name>`은 **유스케이스 다이어그램**(`docs/use_cases.puml`)에서 **단어 그대로 가져온 유스케이스 이름**을 소문자로 바꾸고 공백을 하이픈으로 치환한 것이다. 단어를 바꿔 말하거나, 확장하거나, 순서를 바꾸지 않는다.

| 다이어그램의 유스케이스 이름 | 올바른 파일 이름                       |
|--------------------------|--------------------------------------|
| `Register Account`       | `docs/use_cases/UC-001-register-account.md` |
| `Check In Guest`         | `docs/use_cases/UC-002-check-in-guest.md` |
| `Place Order`            | `docs/use_cases/UC-001-place-order.md` |

## 범위: 유스케이스 하나 또는 여럿

- 작업이 유스케이스 하나를 지목하면(예: "write UC-001 Place Order") **그 파일 하나만** 만든다. 다이어그램의 다른 유스케이스에 대한 명세는 만들지 않는다.
- 작업이 "모든 유스케이스"를 요청하거나 여러 개를 지목하면 **유스케이스마다 파일 하나**를 만든다:
  - `UC-XXX` ID는 다이어그램에서 가져오며 절대 중복되지 않는다.
  - `BR-XXX` 비즈니스 규칙 ID는 **자기 파일 안에서만 유일**하며 **모든 파일에서 `BR-001`로 다시 시작**한다. 유스케이스가 이름공간(namespace)이다. 다른 유스케이스의 규칙을 참조할 때는 유스케이스 ID를 붙여 한정하고(예: "UC-005 BR-002"), 알맹이 규칙 ID만으로 참조하지 않는다.

## 하지 말 것

- 모호하거나 불완전한 시나리오를 작성한다
- 주 성공 시나리오의 단계 번호를 건너뛴다
- 오류 조건에 대한 대안 흐름을 빠뜨린다
- 섹션을 채우기 위해서만 대안 흐름을 지어낸다. 어떤 단계에도 의미 있는 대안이나 예외 조건이 없을 때는 자리표시자로 그렇게 밝힌다(워크플로 9단계 참조)
- 사후 조건을 정의하지 않은 채 남긴다
- 실패에 대한 반응("시스템이 오류 메시지를 표시한다")을 실패 사후 조건으로 적는다. 그것은 대안 흐름의 한 단계이며, 실패 사후 조건은 모든 비성공적 종료에서 성립하는 보장이다
- 기술적 단계(검증, 로드, 영속화)를 사용자 목표인 것처럼 적는다. 워크플로 2단계 참조
- 이벤트나 액터 행동을 사전 조건으로 적는다("사용자가 New Order를 클릭한다"). 그것은 트리거다
- 유스케이스 자신이 확립하거나 평가하는 조건을 사전 조건으로 적는다(날짜가 4단계에서 입력되고 가용성이 5단계에서 확인되는데 "요청한 날짜에 방이 사용 가능하다"라고 적는 것). 그것은 단계이자 대안 흐름이다
- 하나의 문서에 여러 유스케이스를 섞는다
- 흐름 단계에 기술적 구현 세부를 쓴다

## 단계 작성 지침

| 이렇게 쓴다                                  | 이렇게 쓰지 않는다                                         |
|-------------------------------------|-----------------------------------------------|
| "사용자가 예약을 저장한다"        | "사용자가 파란 Save 버튼을 클릭한다"            |
| "사용자가 주문을 확정한다"           | "사용자가 onClick 핸들러를 트리거한다"               |
| "시스템이 이메일 형식을 검증한다" | "시스템이 정규식 /^[\w]+@[\w]+$/를 실행한다"           |
| "시스템이 오류 메시지를 표시한다"     | "시스템이 ValidationException을 던진다"           |
| "사용자가 체크인 날짜를 입력한다"           | "사용자가 dateField 컴포넌트를 채운다"          |
| "시스템이 예약을 저장한다"     | "시스템이 INSERT INTO reservations...를 실행한다" |
| "시스템이 새 계정을 기록한다"    | "시스템이 INSERT INTO users / SELECT ...를 실행한다"  |
| "시스템이 확인 이메일을 보낸다" | "시스템이 sendmail로 SMTP 연결을 연다" |
| "시스템이 비밀번호를 안전하게 저장한다" | "시스템이 bcrypt/SHA + salt로 비밀번호를 해시한다" |
| "시스템이 사용자를 로그인시킨다"          | "시스템이 만료 시간이 있는 JWT를 발급/서명한다" |

단계는 액터와 시스템이 **무엇을** 달성하는지를 설명하며, 그것이 **어떻게** 구현되는지는 결코 설명하지 않는다. 프로토콜과 인프라 용어(SMTP, JWT, bcrypt, hashing, SQL/INSERT/SELECT, HTTP 동사, 클래스와 예외 이름)는 배제한다. 그런 것은 명세가 아니라 구현에 속한다.

## 워크플로

1. `docs/requirements.md`와 `docs/use_cases.puml`, 그리고 존재할 때 `docs/glossary.md`를 읽는다. 액터, 비즈니스 객체, 상태에는 용어집의 용어를 사용하고, 그 Avoid 열에 나열된 동의어는 절대 쓰지 않는다. 유스케이스에 필요한 새 도메인 용어는 용어집에 넣는다(`/requirements` 참조).
2. 문서화할 유스케이스 집합을 정한다(하나, 여럿, 또는 다이어그램의 전부 — 위 "범위" 참조). 다이어그램에서 각 `UC-XXX` ID와 이름을 가져온다. 쓰기 전에 각 유스케이스에 대해 물어본다: *이 유스케이스는 주 액터가 가치 있다고 인식할 완전한 목표인가?* 하위 기능("Validate METAR", "Load NOTAM", "Persist Result")은 더 큰 사용자 목표("Determine Airport Suitability")의 한 단계이고, 요약("Manage Flight Operations")은 여러 목표에 걸친다. 작업을 다른 역할로 넘기거나, 외부 이벤트나 기한을 기다리거나, 서로 다른 액터를 위해 분기를 병렬로 실행하는 시나리오도 요약이다. 그 부분들은 별개의 사용자 목표이고, 그들 사이의 흐름은 유스케이스의 한 섹션이 아니라 BPMN(`docs/processes/`)의 비즈니스 프로세스다. 유스케이스 이름을 바꾸거나, 합치거나, 나누지 않는다 — ID는 다이어그램에 속한다. 명세를 쓴 뒤, 어떤 유스케이스가 하위 기능이나 요약처럼 보이는지, 그것이 어느 사용자 목표에 속하는지 사용자에게 알리고 `/use-case-diagram`으로 넘긴다. 다이어그램이 여러 유스케이스가 공유하는 `<<include>>`로 그리는 하위 기능은 의도된 것이므로 그대로 둔다.
3. **쓰기 전에 명확히 한다.** 각 유스케이스에 대해 [references/clarify-checklist.md](../../../../../plugins/aiwf-core/skills/use-case-spec/references/clarify-checklist.md)(한글 검토본: [clarify-checklist.ko.md](references/clarify-checklist.ko.md))로 출처를 훑고, 답이 명세를 바꾸며 합리적인 기본값이 없는 질문을 사용자에게 한다 — 유스케이스마다 최대 다섯 개, 가장 중요한 것부터, 각각 권장 선택지와 함께. 답은 질문 섹션이 아니라 영향을 주는 단계, 흐름, 규칙에 적는다. 나머지는 최선의 기본값으로 정하고 가정으로 보고한다(16단계). 아무도 답할 수 없을 때(파이프라인 실행, 질문할 방법이 없는 호스트, 또는 사용자가 묻지 말라고 했을 때)는 모든 질문에 권장 선택지를 택하고 역시 가정으로 보고한다. 구현 선택에 대해서는 절대 묻지 않는다 — 그것은 유스케이스에 속하지 않는다.
4. TodoWrite로 진행 상황을 추적한다 — 유스케이스 파일마다 항목 하나.
5. 각 유스케이스의 파일 이름을 위 "파일 이름 규칙"의 규칙으로 도출한다.
6. 개요 섹션을 작성한다: `Use Case ID`, 주 액터, 보조 액터, 목표, 트리거, 그리고 위 "상태 값" 목록의 `Status`. 주 액터는 목표를 추구하는 역할이다. 유스케이스는 흔히 하나지만 여러 개일 수 있다. 각 주 액터가 스스로 유스케이스를 시작할 수 있고 동일한 주 성공 시나리오를 통해 동일한 목표를 추구할 때 쉼표로 구분하여 나열한다(`**Primary Actor:** Front Desk Clerk, Guest`). "or"나 "and"로 잇지 않고 "System"도 쓰지 않는다. 두 역할이 서로 다른 목표를 추구하거나 서로 다른 시나리오를 필요로 하면 그들은 두 개의 유스케이스다. 요구사항이 역할을 구분할 때는 일반적인 "User"보다 요구사항과 용어집에 있는 구체적 역할을 쓴다. 보조 액터는 유스케이스를 지원하거나 유스케이스에 정보나 서비스를 제공하는 역할과 외부 시스템이다(예: `**Secondary Actors:** Weather Service, Flight Planning System`). 구현이 그것들을 시스템의 책임 밖에 있는 것으로, 즉 만들 대상이 아니라 취급하도록 이름을 붙인다. 유스케이스에 보조 액터가 없으면 `**Secondary Actors:**` 줄을 생략한다. `**Trigger:**` 줄(독일어 문서: `**Auslösendes Ereignis:**`, 대안 흐름을 표시하는 `**Auslöser:**`는 절대 아님)은 유스케이스를 시작하는 **이벤트**를 명명한다: 액터의 요청(`Dispatcher requests an airport suitability assessment`), 시점(`End of each business day`), 또는 외부 시스템의 메시지(`Payment Service reports a chargeback`). 트리거는 한 순간에 일어나며, 사전 조건은 이미 참인 상태다. "언제 이것이 일어나는가?"라고 물어 검사한다 — `User is logged in`에는 순간이 없으므로 사전 조건이다. 트리거가 1단계와 일치할 수 있지만 1단계가 그것을 그대로 반복하지는 않는다. `docs/requirements.md`가 있으면 `Status` 줄 뒤에 `**Requirements:**` 줄을 추가한다: 링크 텍스트가 요구사항 ID를 나열하는, 카탈로그로 가는 Markdown 링크 하나로, 이 유스케이스가 실현하는 기능 요구사항(`FR-*`)을 최소한 포함하고, 그것이 준수해야 하는 비기능 요구사항(`NFR-*`)과 제약(`C-*`)도 포함한다. 예(소비 프로젝트의 유스케이스 문서 기준 상대 경로이며 이 저장소의 실제 파일이 아님): `**Requirements:** [FR-001, NFR-004, C-003](../requirements.md)`. ID만 나열하고 요구사항 텍스트를 복사하지 않는다 — `requirements.md`가 단일 진실 공급원(single source of truth)으로 남는다. `/spec-review`는 이 줄로 어떤 유스케이스도 다루지 않는 요구사항과 존재하지 않는 ID를 찾는다. `docs/requirements.md`가 없을 때만 이 줄을 생략한다.
7. 사전 조건을 정의한다 — 유스케이스가 시작되기 전에 참이어야 하는 검증 가능한 사실이다. 그것은 시스템이 이미 확립한 상태이며(흔히 다른 유스케이스에 의해), 이벤트나 액터 행동이 아니고, 유스케이스가 다시 확인하지 않는다. **사전 조건은 유스케이스 동안 확립되거나 평가되는 조건을 설명해서는 안 된다**: 사실이 액터가 단계에서 주는 입력에 의존하거나("요청한 날짜에" 방이 사용 가능함), 어떤 단계가 그것을 확인하거나, 대안 흐름이 그 위반을 처리할 때 그것은 사전 조건이 아니라 주 성공 시나리오와 그 대안 흐름에서 다룰 조건이다. 대신 그것이 기대는 안정된 상태를 유지한다(`Room inventory is configured`).
8. 주 성공 시나리오를 번호가 매겨진 단계로 쓴다(1부터 시작, 빈 번호 없음). 액터 행동과 시스템 응답을 번갈아 쓰고 목표 달성으로 끝난다.
9. **모든** 주 성공 시나리오 단계에서 의미 있는 대안이나 예외 조건을 분석한다 — 액터가 다르게 결정할 수 있는가, 입력이 유효하지 않을 수 있는가, 검사가 실패할 수 있는가, 외부 시스템이 거부하거나 응답하지 않을 수 있는가? 식별한 모든 확장(오류 조건, 선택 경로, 예외 상황)을 문서화한다. 대부분의 실제 유스케이스에는 둘 이상이 있다. 각 확장은 다음을 만족해야 한다:
   - 특정 주 시나리오 단계 번호를 `(step N)`으로 참조하는 **Trigger**를 명명한다(예: `Payment is declined (step 7)`). 그리고
   - `Use case continues at step N.` 또는 `Use case ends.` 중 하나로 끝난다.

   템플릿을 만족시키기 위해서만 대안 흐름을 지어내지 **않는다**. 분석에서 의미 있는 대안이 없으면, 템플릿 흐름을 그 결과를 밝히는 기울임 자리표시자로 바꾼다(예: `_None — no step of the main success scenario can fail or branch._`). 검사기는 자리표시자를 의도된 서술로 받아들이고, 섹션이 비어 있을 때만 경고한다.
10. 성공과 실패 모두에 대해 사후 조건을 정의한다(두 하위 섹션 모두 비어 있지 않아야 함).
   - **Success Postconditions**는 주 액터의 목표가 달성되었을 때 참인 것을 서술한다.
   - **Failure Postconditions**는 유스케이스의 모든 비성공적 종료 — `Use case ends.`로 끝나는 모든 대안 흐름, 취소, 보조 액터의 실패 — 에 대해 성립해야 하는 최소 보장을 설명한다. 그것은 목표가 달성되지 않았을 때 시스템이 보호하는 것(Cockburn의 *Minimal Guarantees*)을 서술하며, 실패에 대응해 시스템이 무엇을 하는지를 서술하지 않는다: "No reservation is created", "Existing valid data is not overwritten", "An incomplete result is never presented as valid", "No partial payment remains booked". 메시지, 알림, 화면 복귀는 보장이 아니다 — 그것은 실패를 다루는 대안 흐름에 속한다. 오직 하나의 실패 경로에만 성립하는 서술은 여기가 아니라 그 흐름에 속한다.
11. 적용 가능한 비즈니스 규칙을 `BR-XXX` ID로 문서화한다. 파일 안에서 `BR-001`, `BR-002`, …로 번호를 매긴다. 모든 파일은 `BR-001`에서 다시 시작하며, 규칙 ID는 자기 유스케이스에 한정된다("범위" 참조).
12. 각 유스케이스를 다음으로 넘어가기 전에 **자기** 파일에 완전히 쓴다 — 두 유스케이스를 하나의 파일로 합치지 않고, 계획한 파일을 쓰지 않은 채 남기지 않는다.
13. 아래 완전성 점검 목록을 실행하고 실패한 항목을 고친다.
14. **최종 검증(완료 선언 전에 수행):** `docs/use_cases/`의 내용을 나열하고, 자기 범위의 모든 `UC-XXX`에 대해 `UC-XXX-<kebab-case-name>.md`(다이어그램 이름의 kebab-case — 예: `Check In Guest` → `UC-002-check-in-guest.md`, `UC-002-checkin-guest.md`가 아님) 형식의 파일이 정확히 하나 있는지 확인한다. 어긋난 이름은 바꾼다. 그런 다음 작성한 모든 파일에 대해 함께 제공된 검사기를 실행한다(스크립트 경로는 이 스킬 디렉터리를 기준으로 함):

    ```bash
    python3 scripts/validate_use_case.py --strict docs/use_cases/UC-*.md
    ```

    보고된 모든 문제를 고치고 깨끗하게 종료할 때까지 다시 실행한다. 오류는 Studio 구조 편집기가 파일을 읽을 수 없음을 뜻하고, 경고는 이 스킬의 규칙 위반을 뜻한다 — 예를 들어 단계에 구현 수준 용어(`SMTP`, `JWT`, `token`, `bcrypt`, `hash`, `SQL`, …)가 있으면 비즈니스 수준으로 다시 써야 한다: 등록 유스케이스는 "System records the new account" / "System confirms the account"라고 하며, 비밀번호가 어떻게 저장되고 세션이 어떻게 생성되는지는 절대 쓰지 않는다.
15. todo를 완료로 표시한다.
16. **품질 게이트 — 넘기고, 스스로 검토하지 않는다.** 검사기는 구조를 확인하지만, 유스케이스가 사용자 목표인지, 액터가 올바른지, 시나리오가 목표에 도달하는지, 실패하는 모든 단계에 흐름이 있는지, 규칙과 사후 조건이 검증 가능한지는 판단할 수 없다. 그 의미 검토는 `/spec-review`다. 어떤 파일을 썼는지 사용자에게 알리고, 3단계에서 명확히 한 것, 가정한 것, 열어 둔 것(보고 형식은 명확화 점검표에 있음)을 나열하고, 유스케이스가 `Reviewed`로 넘어가기 전에 각각에 대해 `/spec-review UC-XXX`(또는 모든 유스케이스를 다 쓴 뒤 프로젝트 전체에 대해 `/spec-review`)를 제안한다. 직접 실행하지 않고, 그 점검표를 여기서 반복하지 않는다 — 검토는 한 곳에서 한 번.

## 완전성 점검 목록

14단계의 검사기가 이 모두를 기계적으로 확인하므로 눈으로 확인하지 말고 실행한다. 이 목록은 완료의 정의로 남는다:

- [ ] 각 파일 이름이 다이어그램의 이름을 사용한 `UC-XXX-<kebab-case-name>.md`이고 정확히 하나의 유스케이스를 문서화한다.
- [ ] 개요에 `Use Case ID`(`UC-XXX`), 하나 이상의 주 액터(쉼표 구분), 목표, 유효한 `Status` 값이 있고, 지원 역할이나 외부 시스템이 참여하면 `**Secondary Actors:**` 줄이 있다.
- [ ] 개요에 유스케이스를 시작하는 이벤트(액터의 요청, 시점, 또는 외부 시스템의 메시지)를 명명하는 `**Trigger:**` 줄이 있다 — 상태가 아니고, 사전 조건의 복사본도 아니다.
- [ ] 사전 조건이 이미 참인 상태이고 이벤트나 액터 행동이 아니며, 유스케이스 동안 확립되거나 평가되는 것이 하나도 없다(어떤 단계도 그것을 확인하지 않고 어떤 대안 흐름도 그것을 다루지 않는다).
- [ ] `docs/requirements.md`가 있을 때 개요에 최소 하나의 `FR-*` ID로 그것을 연결하는 `**Requirements:**` 줄이 있고, 나열된 모든 `FR-*`, `NFR-*`, `C-*` ID가 카탈로그에 존재한다(`/spec-review`가 확인하며 검사기는 아님).
- [ ] 주 성공 시나리오가 1단계에서 시작하고 빈 번호가 없으며, 마지막 단계가 달성되는 목표를 서술한다.
- [ ] 모든 주 성공 시나리오 단계가 대안과 예외 조건에 대해 분석되었고, 의미 있는 것은 모두 대안 흐름이다(보통 둘 이상). 없을 때는 섹션에 지어낸 흐름 대신 기울임 `_None — …_` 자리표시자가 있다.
- [ ] 각 대안 흐름에 특정 주 시나리오 단계 번호를 `(step N)`으로 참조하는 **Trigger**가 있다.
- [ ] 모든 대안 흐름이 `Use case continues at step N.` 또는 `Use case ends.`로 끝난다 — 열린 채로 끝나지 않는다.
- [ ] 성공과 실패 사후 조건이 모두 정의되고 비어 있지 않다.
- [ ] 모든 실패 사후 조건이 유스케이스의 모든 비성공적 종료에 성립하는 최소 보장이다 — 오류 메시지 같은 시스템 반응이 아니고, 단일 실패 경로의 결과도 아니다(`/spec-review`가 판단하며 검사기는 아님).
- [ ] 각 비즈니스 규칙에 `BR-XXX` ID가 있고, 파일 안에서 `BR-001`, `BR-002`, …로 빈 번호 없이 매겨진다. 모든 파일이 `BR-001`에서 시작한다(규칙 ID는 자기 유스케이스에 한정).
- [ ] 어떤 단계에도 기술적 구현 세부가 없다 — HTTP 동사(POST/GET), SQL, 클래스 이름, 정규식, 예외 이름, 프로토콜 용어(SMTP, JWT, bcrypt)가 없다. 위 "단계 작성 지침" 참조.
