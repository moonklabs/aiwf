**식별자:** `workflow`  
**설명:** AIWF 명세 기반 구현, 기존 프로젝트 현대화, 명세 버전 확인과 검토 증거 정리에 사용한다. 유지되는 유스케이스를 현재 코딩 에이전트에 연결하고, 향후 Sprintable 연동에 사용할 로컬 증거를 준비한다.

## 산출물

선택한 사용자 목표 하나에 대해 지속적으로 유지할 요구사항, 유스케이스, 테스트 정의, 코드, 실제 실행한 검사와 검토 packet을 제공한다. 구현을 출시한 뒤에도 명세는 Git에 남는다. 기존 프로젝트 도구와 현재 에이전트를 사용한다. 모델 실행 환경을 설치하거나 특정 공급자를 요구하지 않는다.

## 실행 호스트와의 연결

core 스킬 7개와 선택 가능한 기술 스택 묶음 4개는 보존된 upstream 리소스다. AIWF에 맞추려고 이들의 원문 지시를 수정하지 않는다. 호스트별 처리는 이 workflow와 사용자의 저장소 지침을 통해 적용한다. 보존된 스킬이 `TodoWrite`처럼 사용할 수 없는 도구를 지정하면 호스트의 작업 추적 도구나 짧은 Markdown 체크리스트를 사용한다. 함께 제공되는 스크립트와 참조는 설치된 스킬 폴더를 기준으로 찾는다.

방법론의 기반은 `aiwf-core` 플러그인이다. 선택 확장인 `aiwf-spec` workflow보다 먼저 설치한다. core는 `requirements`, `entity-model`, `use-case-diagram`, `use-case-spec`, `test-case`, `spec-review`, `reverse-engineer`와 관련 검사기를 담당한다. Claude Code는 `/aiwf-core:requirements`처럼 core 스킬을 호출하며, 이 확장은 `/aiwf-spec:workflow`를 제공한다. Codex 설치기는 두 패키지를 포함하고 기존 `aiwf-*` 스킬 이름을 유지한다.

저장소에 맞는 기술 스택을 선택한다. Codex 설치에서는 스택 이름을 접두어로 붙이며, 예를 들어 `aiwf-nestjs-nextjs-implement`가 된다. 명령 참조의 이름 변경은 설치 사본에만 적용한다. Claude Code에서는 해당 `aiwf-*` 플러그인을 설치하고 플러그인 이름을 포함한 명령으로 호출한다. 원래 upstream 에이전트 이름은 유지한다. Angular/Vaadin coverage 스킬에는 `agents/uc-coverage.md` 프롬프트가 포함되어 있다. 파일 설치만으로 Codex 사용자 정의 에이전트가 등록되지는 않는다. 지원되는 호스트에서는 해당 프롬프트로 네이티브 위임을 사용한다. 스킬이 에이전트 기능을 요구하지만 제공되지 않으면 그 부재를 명시한다. 같은 에이전트가 검사했는데 별도 검토자가 실행한 것으로 보고하지 않는다.

upstream 명세의 상태는 문서화된 의미 있는 주장으로 유지한다. digest, 실행 완료, 테스트 통과가 이해관계자 승인을 제공하지 않는다. 되돌릴 수 있는 작업에는 기존 사용자 권한을 따르고, 실제 승인과 검토된 버전을 별도로 기록한다. 구현을 진행하려고 `Approved` 상태를 만들어 내지 않는다. 작성과 검토를 별도 단계로 수행한다. 기존 `.aiwf`와 `.sdd` 파일은 마이그레이션 입력이며 자동으로 제거하지 않는다.

## 진행 절차

1. 저장소 지침, 소스, 기존 테스트와 기존 `.aiwf` / `.sdd` 문서를 읽는다. 관찰된 동작, 요청된 변경, 불확실한 가정을 구분한다. 신규 프로젝트에는 `aiwf-spec init --root <project> --name <name>`을 실행한다. 이 명령은 기존 파일을 보존한다. 기존 프로젝트에서는 `reverse-engineer`로 현재 동작의 초안을 작성하되, 관찰한 모든 동작을 요구사항으로 인정하지 않는다.
2. `docs/vision.md`를 작성하거나 수정한다. 대상 사용자, 처음으로 유용한 결과 하나, 측정 가능한 성공 기준, 범위 밖의 사항과 제약을 정의한다. 선택한 목표에 대해 `requirements`, `entity-model`, `use-case-diagram`, `use-case-spec`, `test-case` 순서로 사용한다. ID를 유지하고 표준 폴더인 `docs/use_cases/`와 `docs/test_cases/`를 사용한다. 파서용 영어 헤딩과 상태 단어를 유지한다. 본문은 한국어로 작성할 수 있다.
3. 설치된 `spec-review/scripts/spec_lint.py --docs <project>/docs --strict --no-baseline`을 실행하고 의미 검토를 별도로 수행한다. 설치된 스킬과 형제 폴더의 상대 위치로 스크립트를 찾는다. 추적성 표는 문서 사이의 연결을 보여 주며 실제 실행된 테스트 커버리지를 뜻하지 않는다. 검토에서 문제가 보고되면 기존 사용자 권한 범위 안에서 별도 작성 단계로 수정하고 관련 검사를 다시 실행한다. lint baseline을 자동으로 수용하지 않는다.
4. `aiwf-spec pin --root <project>`를 실행한다. 로컬 내용 digest를 기록하며 승인을 부여하지 않는다. 필요한 휴먼 승인은 기록된 버전에 대해 실제 승인자가 내리는 별도 결정이다. 에이전트는 사용자가 이미 허용한 로컬 구현을 진행할 수 있다. 진행을 막는 상태를 우회하려고 `Approved`로 바꾸지 않는다.
5. `docs/plans/UC-XXX.md`에 작은 구현 계획을 작성한다. 선택한 UC와 규칙, 변경할 파일, 인수 기준과 테스트 대응, 저장소 테스트 명령, 남은 질문을 적는다. pin 전에 만들거나 추가 후 pin을 명시적으로 갱신한다. 아키텍처 선택은 `docs/architecture/`에 둔다. 각 BR과 대안 흐름에 의미 있는 테스트를 대응시키거나 아직 실행할 수 없는 이유를 명시한다. 테스트 이름에 UC ID가 있어도 전체 커버리지를 증명하지는 않는다.
6. 선택한 목표를 구현한다. 저장소의 현재 스택과 설치된 개발 스킬을 사용한다. 기존 유틸리티와 의존성을 재사용한다. 자명하지 않은 규칙을 강제하는 코드와 관련 테스트에 UC/BR ID를 기록한다. 요청된 변경 밖의 동작을 보존한다. 지원되고 유용할 때만 독립적이고 범위가 한정된 작업을 위임한다. Main이 통합과 검증을 담당한다.
7. 선택한 동작을 입증하는 최소 검사를 실제 실행하고 정확한 출력과 종료 상태를 저장한다. 필요한 더 넓은 검사도 실행한다. 목표를 완료하기 전에 변경 의도, 비교 범위와 실행 근거를 전달하여 `sync-docs`로 영향받는 유스케이스, 규칙, 테스트 정의, 모델과 사용 안내를 갱신한다. 문서에 영향이 없으면 이유를 설명한 변경 없음 결과를 보고한다. 충족하지 못한 요구사항과 의도하지 않은 구현 차이를 보존하고, 정책을 코드에 맞추어 다시 쓰지 않는다. 별도 단계에서 작성 결과를 검토하고 권한이 있는 수정을 해결한 뒤 해당 문서 검사를 실행한다. 구현 뒤 `aiwf-spec check --root <project>`를 실행한다. 명세가 바뀌면 변경을 설명하고 영향받는 동작을 검토한 다음 pin을 명시적으로 갱신하고 관련 테스트를 다시 실행한다. 선택적 업무 프로세스와 테스트 정의도 같은 검토 범위에 포함한다. 동기화는 스킬의 지침을 따르는 작업이며 새 CLI 명령이나 정합성의 자동 증명이 아니다.
8. CLI가 문서화한 checks schema로 증거 JSON 파일을 작성한다. `passed`, `failed`, `not_run`을 구분하고 실제 실행한 검사에는 실제 로컬 로그를 연결하며 미검증 동작을 나열한다. `command`는 설명용 데이터다. packet 생성은 이를 실행하지 않는다. `aiwf-spec packet --root <project> --evidence <file>`을 실행하고 저장된 출력을 확인한다. 에이전트가 보고한 결과를 기록하며 `awaiting_review`, acceptance `not_recorded`를 유지해야 한다.
9. 결과, 변경 파일, 검사와 한계를 보고한다. 업무 수용, 승인, merge와 배포는 각자의 증거가 필요한 별도 주장이다. 현재 CLI는 승인을 강제하거나 자율 스케줄러를 실행하지 않는다.

## Sprintable 연동 경계

이 버전은 로컬 JSON packet만 준비한다. 자동 게시나 동기화는 수행하지 않는다. 향후 어댑터는 정확한 명세·파일 digest와 증거를 담은 Markdown Doc을 만들고, 선택한 story/task에 보고 증거를 연결하며, 필요할 때 문서·개념 승인을 제출해야 한다. 현재 발견된 MCP 계약, 명시적 프로젝트·작업 ID와 반환된 참조를 사용한다. 시각화 산출물의 `spec pins`는 저장소 명세 스냅샷이 아니다. 문서를 업로드했다는 이유만으로 story를 완료 처리하지 않는다. 보고된 증거를 독립 검증으로 취급하지 않는다.

## 종료 조건

선택한 목표에 합의된 검사가 있고, 영향받는 문서를 동기화했거나 이유를 설명한 변경 없음 결과를 기록했으며, 저장한 packet을 다시 읽을 수 있고 남은 공백을 명시했으면 멈춘다. 출력을 늘리기 위해 계획을 반복 생성하거나 변경되지 않은 텍스트를 새로 의미 검토하지 않는다. 중요한 모호성, 파괴적 작업, 권한 부재, 유용하고 안전한 경로가 없는 장애가 있을 때만 상위로 알린다.
