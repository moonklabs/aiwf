# 브라운필드와 그린필드 작업 가이드

작성: 2026-10-04. 상태: 제안, 휴먼 검토 대기.

AIWF의 기존 명세·검증 흐름을 프로젝트의 출발점에 맞춰 적용하는 가이드다. 새로운 스킬이나 CLI 모드를 구현한 기록이 아니다. 상세 역설계는 [깊은 역설계 검토안](DEEP-REVERSE-ENGINEERING.ko.md)을 따른다.

## 출발점과 공통 원칙

| 구분 | 브라운필드: 운영·개발 중인 기존 시스템 | 그린필드: 새 제품·시스템 |
| --- | --- | --- |
| 출발점 | 현재 구현, 사용자 업무, 기존 데이터·연동 계약 | 해결할 문제, 대상 사용자, 제약과 가설 |
| 첫 질문 | 무엇을 개선하며 무엇을 유지해야 하는가? | 누구의 어떤 목표를 먼저 달성할 것인가? |
| 초기 조사 | 현행 동작과 변경 영향 범위 | 요구사항과 중요한 불확실성 |
| 검증 기준 | 보존할 기존 동작 + 요청한 변경 | 명세한 동작 + 실제 사용 가치 |
| 주요 위험 | 회귀, 데이터 손상, 기존 연동과의 비호환 | 잘못된 가정, 과도한 설계, 불필요한 기능 |

두 경우 모두 유스케이스 하나를 문서 → 구현 → 실제 검증까지 연결하고 반복한다. 작업의 종류가 개선, 버그 수정, 신규 기능, 분석 중 무엇인지와 종료 지점을 먼저 정한다. 분석만 요청했다면 구현으로 자동 확장하지 않는다.

## 브라운필드 진행 순서

1. **변경 목표를 먼저 정한다.** 해결할 문제, 기대 결과, 유지할 동작, 이번에 건드리지 않을 범위를 쓴다. 예를 들어 “지출 제출에 승인을 추가하되 기존 조회와 제출 데이터는 유지한다”처럼 구체화한다.
2. **현재 실행 기준을 확보한다.** 커밋·미커밋 변경, 환경, 설정, 스키마 버전과 기존 테스트 결과를 기록한다. 현재 실패도 숨기지 않고 실행 불가, 기존 결함, 원인 미확인으로 분류한다. 기존 실패와 신규 회귀의 구분에 실제 근거를 남긴다.
3. **전체를 얕게, 변경 주변을 깊게 조사한다.** 시스템 지도에서 관련 UC를 고른다. 호출 경로, 공유 데이터, 권한, 외부 연동, 비동기 작업과 사용자 영향을 추적한다. 먼저 모든 기능을 완벽하게 문서화하는 것을 변경 착수의 조건으로 만들지 않는다. 변경 과정에서 영향 범위가 넓어지면 해당 부분을 추가 조사한다.
4. **현행 동작을 근거와 함께 기록한다.** 기존 UC/용어/엔티티 문서를 활용하고 빠진 부분만 복원한다. 중요한 보존 동작에 기존 테스트를 연결하고, 부족하면 현재 동작을 재현하는 회귀 테스트를 보강한다. 알려진 버그를 재현한 결과와 유지할 정상 동작을 구분한다.
5. **변경 차이를 명세한다.** 유지·추가·변경·폐기할 규칙과 대안 흐름, 영향받는 UC, 데이터와 외부 계약을 적는다. 기존 UC가 달라지면 같은 ID를 갱신하고, 독립된 새 사용자 목표라면 새 UC를 추가한다. 같은 엔티티·용어·규칙을 중복 정의하지 않는다.
6. **변경에 맞는 검증과 이전 계획을 정한다.** 기존 동작을 확인하는 회귀 검증과 새 요구사항 검증을 함께 계획한다. 데이터 변경이 있으면 기존 데이터 변환·누락값·재실행을 확인한다. 연동 변경이 있으면 이전·새 호출자의 호환성을 검토한다. 배포가 필요한 범위에서는 단계적 적용, 관찰 항목과 되돌리기 조건을 정한다. 데이터 변환 후에는 단순 코드 롤백만으로 복구되지 않을 수 있다.
7. **작은 범위로 구현하고 비교 검증한다.** 개선과 무관한 대규모 정리를 섞지 않는다. 선택한 UC와 공유 경계의 테스트를 실행하고 필요한 통합·전체 검증을 수행한다. 변경 전후 결과와 미검증 항목을 남긴다. 변경 후 문서는 최신 동작에 맞추고 이전 동작은 Git 이력과 분석 근거에 보존한다.

현행 동작 기록은 업무 정책의 승인이 아니다. 정책이 충돌하면 원하는 동작을 결정할 사람과 질문을 식별한다. 이미 사용자가 지시한 변경과 명확한 로컬 구현은 그 권한 안에서 진행한다.

### 기존 시스템에 신규 기능을 추가할 때

신규 화면이나 서비스라도 인증, 데이터, 이벤트, 배포 환경을 기존 시스템과 공유하면 그 경계를 조사해야 한다. 새 기능만 명세하는 것으로 끝내지 않고 영향받는 기존 UC의 유지 조건과 회귀 검증을 연결한다.

가령 기존 지출 제출에 승인 기능을 더한다면 제출·조회 흐름, 승인 권한, 기존 지출의 초기 상태, 상태 변경 알림, 승인 중 수정 가능 여부와 중복 승인 처리를 확인한다. 이것들은 예시 질문이며 실제 정책은 대상 시스템 조사와 사용자 결정에서 정한다.

## 그린필드 진행 순서

1. **문제와 첫 사용자 목표를 정한다.** 대상 사용자, 해결할 문제, 첫 유용한 결과, 성공을 판단할 기준, 제외 범위를 작성한다. 목표가 모호할 때 요구사항을 다듬고, 코드나 기존 자료에서 확인할 수 있는 내용은 먼저 확인한다.
2. **가정과 제약을 드러낸다.** 핵심 용어, 권한·데이터 정책, 외부 연동, 규모·응답시간 같은 필요한 제약을 정한다. 아직 근거가 없는 것은 가설로 둔다. 검증 가능한 목표에 임의의 수치를 넣어 확정된 요구사항처럼 다루지 않는다.
3. **큰 불확실성만 짧게 검증한다.** 중요한 외부 연동이나 기술 가능성이 불확실하면 제한된 실험으로 확인한다. 사용자 문제가 불확실하면 사용자 업무와 피드백을 확인한다. 실험 결과를 기록하고 필요한 설계 결정을 남긴다. 전체 아키텍처를 먼저 완성할 필요는 없다.
4. **첫 UC의 명세와 테스트를 만든다.** 정상·대안 흐름, BR, 필요한 엔티티와 실패 시 보장을 정의하고 테스트에 연결한다. 사용자 목표에 필요한 범위의 설계를 선택한다. 여러 UC를 미리 상세하게 작성하느라 첫 결과를 늦추지 않는다.
5. **첫 UC를 끝까지 구현한다.** UI가 필요하면 UI부터 서비스·저장·필요한 연동까지 한 흐름을 연결한다. 필요한 프로젝트 실행·테스트 도구와 자동 검사를 마련한다. 실제 입력으로 동작과 오류 흐름을 확인하고 미검증 환경을 명시한다.
6. **사용 결과로 명세를 갱신하고 확장한다.** 테스트 통과와 사용 가치 검증을 구분한다. 사용자 피드백으로 요구사항과 용어를 수정하고, 다음 UC를 같은 방식으로 추가한다. 구현이 생긴 영역은 이후 변경 때 현행 조사와 회귀 검증을 적용한다.

새 저장소도 기존 플랫폼·인증·DB·외부 API를 사용할 수 있다. 내부 구현은 그린필드여도 그 공유 경계에는 브라운필드의 영향 분석을 적용한다.

## AIWF에서의 연결

- 브라운필드: `reverse-engineer`로 필요한 현행 명세를 복원한 뒤 변경 요구사항 → UC/엔티티 갱신 → `test-case` → `spec-review` → 구현·검증으로 이어간다.
- 그린필드: `requirements`로 목표·요구사항·용어를 정리하고 필요한 엔티티와 UC → `test-case` → `spec-review` → 첫 구현·검증으로 이어간다. 모호한 목표는 로컬 `grill-with-docs`를 사용할 수 있으나 이 스킬은 현재 core에 내장된 것이 아니다.

형식 검사와 의미 검토 후 계획까지 작성한 명세를 `pin`하고, 구현 후 `check`로 문서 변경을 확인하고 `packet`으로 검증 자료를 묶을 수 있다. 기존 자료는 보존하며 `pin`의 필수 문서·UC/TC 조건을 충족해야 한다. 명세가 바뀌면 변경 근거를 기록하고 기준을 갱신한 뒤 영향받는 검증을 다시 수행한다.

현재 CLI는 역설계, 테스트 실행, 검증 증거의 코드 버전 일치나 휴먼 승인을 자동 보장하지 않는다. 실험·테스트는 프로젝트 도구와 에이전트가 실행하고 정확한 버전·환경·로그를 연결한다. 기능을 병합·배포·업무 수용했다는 판단은 각각의 증거가 필요하다.

## 최소 문서와 휴먼 리뷰

`docs/vision.md`, `requirements.md`, `glossary.md`, `entity_model.md`, `use_cases.puml`과 선택한 UC/TC를 점진적으로 관리한다. 이미 자료가 있으면 그 기준과 연결하며 중복 작성하지 않는다. 브라운필드는 현행 근거와 영향 분석을 `docs/architecture/`에 추가하고, 변경 계획은 `docs/plans/UC-XXX.md`에 둔다. 그린필드는 필요한 설계 결정과 확인하지 못한 가정을 같은 경로에 남긴다.

문서 본문은 사람이 읽을 수 있는 한글로 작성하고 core 파서용 헤딩·ID·상태는 유지한다. 관찰된 사실, 변경 목표와 남은 질문이 한 문장 안에서 섞이지 않도록 쓴다. 원문 스킬을 고도화하면 별도 한글 검토본과 관리 목록을 같은 변경에서 갱신한다.

사람에게는 문서 전체를 반복해서 승인받기보다 유지·변경할 정책, 발견된 충돌, 중요한 설계 선택과 미검증 항목을 명확히 제시한다. 검토한 버전을 기록하고 자동 검사를 사람의 승인으로 바꾸지 않는다.

## 개발 후 현재 기준으로 문서를 유지하는 절차

추가 검토 및 반영: 2026-10-04. 문서 동기화는 AIWF 소유 [sync-docs 원문](../../plugins/aiwf-spec/skills/sync-docs/SKILL.md)과 [한글 검토본](../ko-skills/aiwf-spec/skills/sync-docs/SKILL.ko.md)에 반영했고 workflow의 완료 단계에도 연결했다. 변경 영향 분석·다른 스택의 감사 절차 확대는 후속 검토 사항이다. 아래 가이드가 실제 제품에서 검증되거나 휴먼 승인된 것을 뜻하지 않는다.

개발 완료 시 코드뿐 아니라 영향받는 요구사항·UC·BR·테스트 정의·엔티티·설계·사용 안내가 함께 정리되어야 한다. 매번 전체 문서를 다시 생성하는 방식보다 변경 영향에 따라 기존 문서를 갱신하는 방식으로 운영한다. 문서 영향이 없다면 조사 범위와 그 이유를 남긴다.

“현재”는 작업 브랜치의 구현 버전과 실제 배포 버전을 구분해야 한다. 새 기능이 브랜치에 구현되었다는 이유로 운영 중인 기능이라고 설명하지 않는다. 아직 구현되지 않은 요구사항은 목표로 남기고, 구현·검증·배포 여부와 근거를 별도로 기록한다. 이 표현은 기존 core 상태 값을 바꾸는 새 파서 규약이 아니다.

### 작업마다 수행할 정리

1. **개발 전 영향 목록을 작성한다.** 변경 목표와 diff, 관련 호출자·공유 데이터·권한·이벤트 경계에서 영향받는 UC와 문서를 식별한다. 코드 파일명만으로 문서 대상을 결정하지 않는다.
2. **개발 중 명세와 구현의 차이를 기록한다.** 요청한 변경이면 관련 명세를 갱신한다. 승인·합의된 의도에 어긋나는 구현이면 코드 결함으로 다룬다. 어느 쪽이 맞는지 불분명하면 충돌로 기록하고 필요한 판단을 요청한다. 코드에 맞추기 위해 요구사항을 무조건 완화하지 않는다.
3. **검증 후 영향받는 문서를 함께 갱신한다.** UC의 흐름·규칙·사후조건, UC 다이어그램, 데이터·상태 모델, 테스트 시나리오와 실제 구현 연결을 확인한다. 사용법·설정·API 계약·배포 방식이 바뀌면 관련 README와 운영 안내도 반영한다. 설계 결정 기록은 기존 결정의 역사적 이유를 덮어쓰지 않고 후속 결정과 연결한다.
4. **ID와 링크를 유지한다.** 같은 사용자 목표는 같은 UC ID로 갱신한다. 신규 목표는 새 ID를 부여한다. 폐기·병합한 항목은 대체 항목과 이력을 남기고 끊어진 참조를 해결한다. 사용한 ID를 다른 목표에 재사용하지 않는다. 중요한 BR 연결과 테스트 이름이 변경 과정에서 의미를 잃지 않았는지 확인한다.
5. **작성과 검토를 나눈다.** 작성 단계가 정리한 문서에 대해 별도 검토 단계에서 코드·명세·테스트 연결과 문서 간 일관성을 확인한다. 독립 에이전트가 없으면 별도 검토 단계였음을 밝히고 독립 리뷰라고 주장하지 않는다. 코드에 테스트가 있다는 사실과 그 테스트를 실행해 통과했다는 사실을 구분한다.
6. **최종 변경분에 맞는 증거를 남긴다.** 변경 후 테스트 결과와 문서 정합성을 확인하고 남은 미검증 항목을 기록한다. 명세가 변경되면 이유를 설명하고 pin 갱신과 영향받는 테스트 재실행을 수행한다. 문서·코드·검증 근거를 같은 PR에서 검토할 수 있게 한다. 과거 실행 로그를 현재 코드의 검증 근거처럼 재사용하지 않는다.

종료 시 결과에는 영향받은 UC/BR/TC, 갱신 문서, 코드·실행 근거, 남은 불일치·미구현·미검증 항목을 포함한다. 문서가 최신이어야 한다는 요구는 아직 구현하지 않은 목표나 확인하지 못한 조건을 삭제하는 이유가 되지 않는다.

### 필요한 역량과 기존 스킬의 범위

| 역량 | 현재 활용할 것 | 보강할 부분 |
| --- | --- | --- |
| 변경 영향 분석 | `reverse-engineer`와 기존 문서·코드 조사 | diff에서 공유 경계를 따라 영향 UC·문서·테스트를 정하는 재사용 절차 |
| 문서 갱신 | `requirements`, `use-case-spec`, `use-case-diagram`, `entity-model`, `test-case` | 변경 후 이 스킬들의 작성 범위를 묶고 최신 상태를 정리하는 절차 |
| 문서 정합성 검토 | `spec-review` | 구현 후 영향 문서를 대상으로 다시 검토하는 완료 조건 |
| 명세와 구현·테스트 대조 | Angular/JPA, Vaadin/jOOQ의 `coverage-check` | 다른 스택에서 사용할 공통 대조 절차와 실제 실행 증거 연결 |

`spec-review`는 문서를 서로 대조하며 코드 구현을 검사하는 스킬이 아니다. 현재 두 `coverage-check` 스킬은 읽기 전용 보고를 작성하고 코드·명세를 수정하거나 테스트를 실행하지 않는다. `aiwf-spec check`도 명세 파일 해시를 비교하므로 문서가 코드에 맞게 최신이라는 증명으로 사용할 수 없다.

AIWF 소유 `workflow`는 완료 전에 `sync-docs`를 사용하도록 갱신했다. 단독 문서 정리에도 재사용할 수 있으며 입력은 기준 버전·변경 범위·변경 의도, 출력은 영향 목록·문서 갱신·불일치 보고와 검증 근거다. Codex 프로젝트 설치기는 `aiwf-sync-docs`로 설치하고 Claude Code는 `/aiwf-spec:sync-docs`로 호출한다. 이 checkout에는 추가되어 있으나 원격 설치에 사용하려면 해당 변경의 게시가 필요하다. 스킬 지시 추가는 자동 동기화 서비스나 정합성 강제 장치의 구현이 아니다.

공통 코드·명세 대조 역시 필요한 역량이지만 기존 스택의 감사 절차를 복제해 별도 기준을 만들지 않는다. 사용할 범위와 책임을 정한 뒤 기존 core 형식과 감사 규칙을 연결한다. 필요 시 영향 분석을 별도 스킬로 분리하되 먼저 workflow에서 반복 사용과 누락을 관찰한다.

실행 지시를 반영하는 후속 변경에서는 AIWF 소유 원문과 한글 검토본, 플러그인 README 양쪽, 카탈로그·manifest를 변경 범위에 맞춰 함께 갱신한다. upstream core의 원문은 보존한다.
