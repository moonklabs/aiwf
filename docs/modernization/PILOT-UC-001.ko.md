# UC-001 파일럿 계획과 종료 기준

작성: 2026-10-03. 상태: **로컬 예제 실행 완료, 실제 제품 적용·휴먼 리뷰 대기**. [Claude 두 세션의 지적](CLAUDE-PLAN-REVIEW-2026-10-03.ko.md)을 반영한다. 실행 전 정한 범위와 기준을 아래에 유지하고 실제 결과는 [별도 기록](PILOT-RESULT-2026-10-03.ko.md)으로 연결한다.

## 이번에 실행할 범위

소비 프로젝트가 아직 지정되지 않아 기존 지출 제출 예제를 별도 임시 프로젝트로 구성한다. `UC-001`의 서비스 부분과 현재 CLI의 명세 고정·변경 감지·검증 packet 흐름을 실행한다. 이것은 실제 회사 제품의 도입 파일럿이나 새 프로젝트 개발 시간 비교가 아니라 **로컬 예제의 실행·변경 검증**이다. 실제 소비 프로젝트 경로와 UC는 사용자에게 별도로 요청했다.

기준 자료는 [명세 예제](../../examples/spec-workflow/README.md)와 [이전 서비스 구현·테스트](evidence/full-test-20261003/)다. 과거 실행 결과를 복사해 이번 성공으로 표시하지 않고, 현재 도구로 다시 실행한다. historical 파일은 수정하지 않는다.

이번 변경은 엔터티 모델에 이미 적힌 `description` 길이 200을 UC·테스트·구현에 명시적으로 연결하는 것이다. 예제 파일럿의 “자”는 Unicode code point로 정의한다. 빈 문자열·생략·null은 빈 사용 내용으로 취급하고, 그 밖의 입력은 문자열이어야 한다. 실제 제품의 글자 수·null·공백 정책 결정으로 확대하지 않는다.

## 실행 순서

1. 기준 예제의 명세와 기존 서비스·12개 테스트를 임시 프로젝트에 복사한다. 구현 계획과 UC/BR/TC→검사·미검증 표를 `docs/plans/UC-001.md`에 먼저 작성한다.
2. 현재 Python 구조 검사와 서비스 테스트를 실행하고 실제 로그·exit code를 남긴다. 명세를 pin한 뒤 기준 packet을 생성·읽어 확인한다.
3. 임시 프로젝트의 명세에 `BR-002` 사용 내용 조건과 A3 길이 오류, 대응 TC 검증을 추가한다. pin 갱신 전에 `check`와 `packet`이 drift를 보고·거부하는지 확인한다.
4. 구조·의미를 별도로 확인한 뒤 pin을 명시적으로 갱신한다. 새 요구사항을 검증하는 테스트를 추가하고 **구현 수정 전의 실제 실패**를 기록한다. 실패 packet도 남긴다.
5. 임시 프로젝트의 서비스 구현을 수정해 길이·타입·선택 입력을 검증한다. 동일 명세와 새 테스트를 다시 실행하고 새 로그로 최종 packet을 만든다.
6. 정상·대안·실패 흐름과 미검증 범위를 로그·테스트 이름·명세 ID로 확인한다. 실제 사람 검토를 위한 한국어 기록 양식을 남긴다.

## 명세·검사 정의의 위치와 책임

이번 파일럿의 구현 계획·명세와 검사 연결표는 `docs/plans/UC-001.md`에 둔다. 이 경로의 Markdown은 현재 CLI의 pin 대상이다. 명령을 자동 실행하는 설정 파일이 아니며, 현재 에이전트가 요청된 범위의 프로젝트 도구를 사용해 실행한다.

| 정의 | 책임·버전 확인 |
| --- | --- |
| UC·소속 BR·TC·검사 연결, 실제 명령, 입력 파일, 미검증 이유 | 소비 프로젝트의 `docs/plans/UC-001.md`; 명세 pin에 전체 파일 포함 |
| 실행 당시 코드·테스트 hash, 명령 argv·cwd, 시각·exit code·로그 hash | 이번 실행 기록에 보관; 현재 CLI가 자동 확인한다고 주장하지 않음 |
| 이후 CLI 실행 계약을 확장할 경우 | AIWF의 `aiwf-spec`/CLI 소유. upstream core의 형식·원문은 수정하지 않음 |

향후 runner의 최초 후보는 이 계획 안의 명시적인 검사 ID·argv·입력 파일 목록을 사용하는 방식이다. 파서/schema는 아직 채택하지 않는다. runner 착수 시에는 선택한 계획의 bytes와 pin 일치, 선택한 검사 ID·실제 argv, 실행 전후 입력 hash를 연결해야 한다. 계획·매핑·명령이 바뀌면 기존 결과를 최신 검증으로 재사용하지 않는다. 이미 부여된 실행 권한을 별도 `--yes`로 다시 요구하는 절차는 기본 계약으로 넣지 않는다.

## 검증과 완료 조건

| 항목 | 이번 로컬 실행의 완료 조건 |
| --- | --- |
| 기준선 | 구조 검사와 기존 서비스 12개 테스트의 실제 실행 기록, 기준 pin·packet readback |
| 명세 변경 | 구조 검사 통과, pin 전 drift 탐지, drift 상태 packet 생성 거부 |
| 요구사항 대비 구현 | 길이 초과를 구현 수정 전 테스트가 실패로 검출, 수정 후 동일 검사 통과 |
| 실패 보존 | 실패 검사·미실행 검사를 포함한 packet 생성·readback; packet 생성 성공을 테스트 성공으로 표시하지 않음 |
| 최종 결과 | 새 로그로 최종 packet 생성, `awaiting_review`·acceptance `not_recorded`, pin/spec digest 일치 |
| 재현성 | 최종 docs/src/tests, 실행 명령·exit code·입력·로그 hash 보관; 새 프로세스에서 서비스 검사 재실행 |
| 문서 | 원문·한글 README·관련 기록 갱신과 `npm run docs:check` 통과 |

위 항목은 에이전트의 로컬 검증 완료 기준이다. 실제 소비 프로젝트의 파일럿 완료에는 사용자 지정 프로젝트·UC와 실제 검토자의 결과가 추가로 필요하다. 예제 실행만으로 그 단계를 완료했다고 기록하지 않는다.

오류가 있는 자료를 성공으로 묶으면 해당 단계를 수정·재검증한다. 알려지지 않은 도구·입력·의미 판단은 미검증으로 남긴다. 환경 접근이나 정책상 실행 불가가 발생하면 성공 기록 없이 원인을 보관한다. 반복 루프나 자동 retry를 새 기능으로 추가하지 않는다.

## 측정과 확장 판단

이번에는 각 명령의 실제 시작·종료 시각과 프로세스 wall time, 실제 로그, 실패·미실행·전사 항목을 기록한다. 에이전트의 편집·검토 시간이 사람의 활성 작업 시간이나 개발 생산성을 뜻하지 않으므로, 사람이 측정하지 않은 값은 `not_measured`로 둔다. 같은 UC를 연습·재실행한 시간은 독립적인 두 UC의 비교 자료로 쓰지 않는다.

실제 제품 적용을 위한 탐색 기준은 **비교 가능한 독립 UC 2개 이상에서 같은 준비·전사 작업이 반복되고, 측정한 사람의 활성 시간이 합계 10분 이상**일 때 해당 자동화의 최소 범위를 검토하는 것이다. 10분은 이번 계획의 제안 기준이며 입증된 손익이나 일반 기준이 아니다. 사용자와 실제 기록에 맞춰 조정할 수 있다. 결정적 검사 누락·오래된 로그 오인은 시간과 별개로 정확성 문제로 우선 처리한다.

기준을 충족해도 자동으로 기능을 추가하지 않는다. 실행·기록·유지비용과 범위를 비교한다. 자동화 없이 자료 준비가 충분하면 **새 기능 없이 파일럿을 종료**한다. 이번 예제 한 번의 결과로 runner·packet v2·문서 보고서·병렬 실행 도입을 결정하지 않는다.

## 실제 사람의 검토 기록

사용자의 “진행”은 작업 실행 지시다. 아래 항목의 의미 검토·업무 수용을 대신하는 기록으로 사용하지 않는다.

| 항목 | 기록할 값 |
| --- | --- |
| 검토자 / 검토 시각 | 아직 미기록 |
| 읽은 packet / 명세 digest / 코드·테스트 hash | 실제 검토 시 기록 |
| 범위에 대한 판단 | 수용 / 수정 요청 / 판단 보류와 이유 |
| 자료 부족으로 재요청한 항목·횟수 | 실제 검토 시 기록 |
| 기능·명세 의미 때문에 수정한 항목 | 자료 준비 문제와 구분 |
| 리뷰 준비·읽기·수정에 쓴 활성 시간 | 사람이 측정한 값만 기록 |

## 남는 미검증 범위

- 로그인·제출자 계정·실제 권한·submitter_id 관계.
- UI 입력·오류 메시지·접수 화면·브라우저 TC 전체 흐름.
- 실제 DB·프로세스 간 지속성·동시성·금액 Decimal 정밀도.
- 실제 업무 규정·고객 요구·제품 도입 효과·휴먼 수용.
- 지원 하한 Node 20/Python 3.9, stack별 앱, Sprintable·원격 승인·무인 실행.

실행 결과는 별도 기록으로 연결하고, AI 리뷰나 자동 검사만으로 이 목록을 지우지 않는다.
