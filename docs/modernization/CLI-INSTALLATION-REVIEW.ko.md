# CLI 설치 중심 역할 검토

작성: 2026-10-05. 기준: 현재 작업 트리의 코드·문서와 임시 프로젝트 실행 결과.

상태: **설치 CLI `0.5.0` 작업 트리 구현, `awaiting_review`**. 공개 `aiwf` 진입점·설치·카탈로그·상태 조회를 구현했다. npm 게시, 저장 프로필, 스킬 갱신·제거와 네이티브 플러그인 자동 설치는 후속 범위다. 현재 npm 배포판은 여전히 `0.4.0`이다.

후속 사용자 결정: 일반 사용자는 `npm i -g aiwf`로 CLI를 설치하고 `aiwf install`을 사용한다. 일회 실행용 `npx aiwf`는 보조 경로다. 스킬 배치는 공식 skills CLI를 우선 활용하고 AIWF는 카탈로그·구성 선택·리소스 준비·충돌 확인·설치 상태를 담당한다. CLI의 npm 전역 설치와 스킬의 프로젝트/사용자 설치 범위는 독립된 선택이다.

구현 범위: 공개 `aiwf` 진입점, Codex/Claude 스킬 설치, 프로젝트·사용자 범위, core/spec·복수 스택·선택 위임, dry-run, 동일 구성 반복·추가 설치, 상태 조회. 기존 `aiwf-spec`와 `aiwf spec`로 명세 기능을 사용할 수 있다.

## 구현한 설치 계약

- `npm i -g aiwf`가 CLI와 고정된 `skills@1.7.0` 의존성을 함께 설치한다. 별도 skills 전역 설치나 매번 최신 `npx` 실행이 필요 없다. 이 backend는 Node.js **22.20 이상**을 요구해 패키지 요구 버전도 올렸다. [배포 메타데이터](https://registry.npmjs.org/skills/1.7.0).
- [`aiwf` CLI](../../src/cli/aiwf-cli.js)는 `install`, `list`, `status`, `spec`를 제공한다. 대화형 설치는 호스트·스택·위임을 선택하고 자동 실행은 `--agent`를 지정한다. CLI 전역 설치와 스킬의 `--global` 옵션은 별개다.
- [공유 카탈로그와 리소스 준비](../../src/lib/skill-bundles.js)는 marketplace 기준으로 core와 선택 항목을 계산한다. core+spec를 추천하고 `--core-only`로 spec를 제외한다. 복수 스택은 이름을 분리하며 위임은 기본 설치에서 빠진다. 원문은 수정하지 않고 설치 자료에만 이름·참조 매핑을 적용한다.
- [설치 관리](../../src/lib/skill-installation.js)는 패키지 내부 skills 실행 파일을 Node로 호출한다. 호스트·스킬을 명시하고 `--copy --yes --json`을 사용하며, CLI 종료 상태와 실제 설치 자료의 해시를 확인한다.
- 기존 AIWF 관리 파일이 기록된 버전·내용과 같으면 건너뛴다. 스택·위임·다른 호스트를 나중에 추가할 수 있다. 다른 도구가 설치했거나 수정된 목적지는 보존하고 충돌로 표시한다. 이전 checkout 전용 설치 파일을 자동으로 AIWF 관리 대상으로 전환하지 않는다.
- `.aiwf/skills-installation.json`은 호스트·버전·소스와 설치 파일 해시를 기록한다. 실패 중 실제 확인된 설치는 기록해 재시도 때 유지한다. 불완전하거나 수정된 디렉터리는 자동으로 지우지 않는다.
- `.aiwf/skill-sources/`는 설치용 정식 자료로 보존한다. 공식 skills CLI가 만드는 `skills-lock.json`이 삭제된 임시 소스를 가리키지 않도록 하기 위한 것이다. 최초 준비 과정의 임시 폴더는 정리한다. 외부 스킬 추적 정보가 있는 정상 lockfile은 유지하며 손상·심볼릭 링크는 설치 전 거부한다.
- Codex의 프로젝트·사용자 스킬은 `.agents/skills`에, Claude 프로젝트 스킬은 `.claude/skills`에 설치한다. Claude 사용자 범위는 `CLAUDE_CONFIG_DIR`를 따른다. 이는 고정한 skills backend의 경로 계약이며 네이티브 플러그인 캐시와 다르다. [고정 버전 경로 구현](https://github.com/vercel-labs/skills/blob/7407f3893ad4dceab546ac002c3ef806e4000c73/src/installer.ts#L118-L164).

스킬은 실제 설치 후 해당 호스트에서 사용한다. 네이티브 플러그인 자동 등록·MCP 구성·모델 인증·교차 CLI 실행은 설치의 부수 효과에 포함하지 않는다.

## 권고

CLI의 첫 역할은 **사용자가 필요한 AIWF 플러그인·스킬 구성을 선택하고, 사용하는 에이전트에 한 번의 흐름으로 설치·유지할 수 있게 하는 것**으로 정한다. AIWF 방법론의 목적은 유스케이스·구현·검증·최신 문서를 연결하는 것이며, CLI는 그 방법론을 쉽게 도입하는 입구가 된다.

설치가 끝나면 실제 설치된 스킬의 호출 이름과 한글 사용 안내를 제공한다. 기존 `aiwf-spec`의 문서 초기화·pin·drift·packet은 계속 사용할 보조 기능이다. 설치 우선순위를 높인다고 스킬의 문서 관리 절차나 기존 명세 CLI를 제거하지 않는다.

“한 번에 설치”는 모든 스킬을 무조건 설치한다는 뜻이 아니다. 프로젝트에 맞는 구성을 한 번 선택하고 적용한다는 뜻이다. 커스터마이징의 첫 범위는 **호스트·설치 범위·플러그인 조합·선택 위임·버전**이다. 스킬 원문 편집과 프로젝트별 규칙은 구분해 갱신 때 사용자 변경을 보존한다.

## 개선 전 상태와 확인한 문제

다음 표와 기존 복사 설치 재현은 새 공개 CLI 추가 전의 기준이다. checkout 전용 복사 스크립트는 기존 중단 계약을 유지하고 공유 카탈로그·리소스 준비 함수를 재사용한다.

| 항목 | 근거와 현행 동작 | 사용자에게 미치는 영향 |
| --- | --- | --- |
| 공개 실행 파일 | [package.json](../../package.json)의 `bin`에는 `aiwf-spec`만 있다. [명령 정의](../../src/cli/spec-cli.js)는 `init`, `pin`, `check`, `packet`이다. | `aiwf install`을 설치 입구로 사용할 수 없다. `init`은 명세 문서 생성이다. |
| 별도 설치 스크립트 | [install-spec-skills.mjs](../../scripts/install-spec-skills.mjs)는 core 7개와 spec 2개를 기본 설치한다. 스택 하나와 Claude/Codex 위임을 선택할 수 있다. | 조합 설치의 기반은 있으나 일반 사용자가 checkout 안의 스크립트 경로를 알아야 한다. |
| 설치 대상 | 스크립트는 프로젝트의 `.agents/skills`로 복사한다. 호스트·사용자 범위 선택은 없다. | Claude/Codex 설치 경험을 같은 입구에서 제공하지 못한다. `--delegate claude`는 설치 호스트 선택이 아니라 위임 스킬 선택이다. |
| 구성 선택 | `aiwf-spec`는 README에서 선택 항목이지만 스크립트에서는 항상 포함한다. `--stack`은 하나만 받는다. | 최소 core, 복수 스택, 저장한 구성 재사용이 불가능하다. |
| 반복·추가 설치 | 목적지 중 하나라도 존재하면 전체 설치를 거부한다. | 기본 설치 이후 스택을 추가할 수 없다. 같은 구성 재실행도 실패한다. |
| 설치 관리 | 출처·버전·설치한 파일의 해시·설치 관리자를 연결하는 설치 기록과 갱신·제거 명령이 없다. | 동일 파일, 로컬 수정, 다른 도구가 설치한 파일을 구분해 안전하게 관리하기 어렵다. |
| 카탈로그 | [marketplace](../../.claude-plugin/marketplace.json)와 스크립트의 스택 목록이 따로 있다. 플러그인 간 의존성은 설치용 데이터로 선언돼 있지 않다. | 새 플러그인 추가 때 목록이 어긋나거나 필요한 core가 빠질 수 있다. |

기존 파일 충돌 사전 확인과 덮어쓰기 거부는 사용자 파일을 보호하는 장점이다. 새 공개 CLI는 이를 유지하면서 **AIWF가 설치한 동일 버전은 건너뛰고 새로 선택한 항목만 추가**한다. 무조건 덮어쓰는 플래그는 추가하지 않았다.

복사는 순차 실행되므로 중간 I/O 오류가 나면 일부 파일이 남을 가능성도 있다. 이는 코드에서 확인한 실패 처리 공백이며, 이번 검토에서 디스크 오류를 주입해 재현한 결과는 아니다.

## 실제 실행으로 확인한 범위

새 임시 프로젝트에서 현재 설치 함수를 실행했다. 실제 사용자 프로젝트나 사용자 전역 스킬은 변경하지 않았다.

| 시나리오 | 결과 |
| --- | --- |
| 기본 dry-run | 9개 목적지 |
| Electron 선택 dry-run | 15개 목적지 |
| Electron + Claude/Codex 위임 선택 dry-run | 17개 목적지 |
| 기본 실제 설치 | 9개 설치 |
| 같은 프로젝트에 기본 설치 반복 | `Skill already exists; no files overwritten`로 중단 |
| 같은 프로젝트에 Electron 추가 | 기존 `aiwf-entity-model` 목적지에서 같은 오류로 중단 |
| 중단 후 파일 확인 | 기존 core는 보존, Electron 스킬은 추가되지 않음 |

임시 프로젝트는 실행 직후 삭제했다. 일회성 테스트·검증 스크립트는 저장소에 추가하지 않았다. Electron 15개·17개 구성은 이번에는 설치 계획만 확인했으며, 호스트의 스킬 로딩·모델 실행 성공을 뜻하지 않는다.

## 설치 사용 흐름

다음 명령은 **`0.5.0` 게시 후의 기본 사용 흐름**이다. 배포 전에는 README의 checkout 실행 경로를 사용한다.

```bash
npm i -g aiwf
aiwf install

# 같은 선택을 비대화형으로 재현하는 예시
aiwf install --agent codex --stack electron-react --delegate claude --dry-run
aiwf install --agent codex --stack electron-react --delegate claude
aiwf status
```

1. 설치할 프로젝트와 호스트를 선택한다. Codex, Claude Code 또는 둘 다를 명시한다.
2. 프로젝트 범위는 기본값이며 다른 프로젝트는 `--project`, 사용자 범위는 `--global`로 지정한다.
3. core + workflow/sync-docs를 추천 구성으로 제시하고, core만 사용하는 구성도 허용한다.
4. 필요한 기술 스택과 위임 애드온을 선택한다. 위임은 기본 해제한다. 여러 스택은 의존성과 이름 충돌을 검증한 조합만 허용한다.
5. 설치 계획에 추가·유지·충돌, 설치 위치, 버전, 관리 방식을 표시한다. `--dry-run`은 이를 파일 변경 없이 제공한다. 버전이 다른 기존 설치는 충돌로 표시하며 자동 갱신하지 않는다.
6. 선택한 항목을 적용하고 결과와 실패 항목을 기록한다. 같은 구성을 다시 실행하면 변경 없는 성공이어야 한다.
7. 실제 설치된 호출 이름, 다음 작업 예시, 패키지에 포함한 `README.ko.md`와 전체 한글 검토 자료 위치를 안내한다. 온라인 전체 검토 자료는 현재 main 링크이므로 설치한 패키지 버전의 검토 완료로 해석하지 않는다.

설치 완료 후 브라운필드 사용자는 역설계로, 그린필드 사용자는 요구사항 작성으로 시작할 수 있게 안내한다. 설치 명령 자체가 역설계·앱 생성·에이전트 실행을 자동 시작하지는 않는다.

## 구현 범위와 후속 책임

| 순서 | 범위 | 완료 기준 |
| --- | --- | --- |
| 구현 | 공개 `aiwf` 진입점, 플러그인 카탈로그·의존성, 설치 대상 선택, 계획/적용 | checkout 내부 경로를 몰라도 추천 구성·스택·위임을 한 흐름에서 설치한다. core 의존성과 동반 리소스가 빠지지 않는다. |
| 구현 | 설치 기록, 기존 설치 판별, 안전한 반복·추가 설치 | 같은 구성은 변경 없이 성공하고, 기존 core를 유지한 채 스택을 추가한다. 로컬 수정·관리자 불명 파일은 충돌로 표시하고 보존한다. |
| 구현 | 설치 상태 조회와 결과 안내, `aiwf spec` | 설치 위치·구성·버전·관리 방식과 실제 호출 이름을 확인한다. 부분 실패를 성공으로 보고하지 않는다. 기존 `aiwf-spec` 사용법을 유지한다. |
| 후속 | 저장 가능한 선택 프로필, 관리 대상 갱신·제거 | 다른 프로젝트에서 같은 구성을 재현한다. AIWF가 소유한 항목만 관리하고, 제거 시 의존성을 확인한다. |
| 후속 | 네이티브 플러그인 자동 설치·검증 자동화 | 실제 호스트의 지원 계약과 반복 작업 근거를 확인해 확장한다. |

설치 기록에는 요청한 구성과 실제 확정 버전·파일 해시·호스트·설치 범위·설치 관리자를 구분해 남기는 것이 적합하다. 배포판 버전, 플러그인 버전, Git 소스 기준도 구분해야 한다. 다운로드나 파일 복사 단계의 실패는 적용 결과를 남기고, 복구는 해당 실행이 관리하는 파일로 한정한다.

첫 구현은 플러그인 단위 조합을 우선한다. 개별 스킬 선택은 sibling 검사기·참조 문서·규칙·다른 스킬 호출의 의존성을 계산할 수 있을 때 지원한다. 현재 core 7개 중 이름 하나만 골라 복사하는 방식으로 축소하면 실행 리소스가 누락될 수 있다.

AIWF는 조합·의존성·설치 정책·문서 안내를 담당하고, 실제 배치는 호스트의 공식 플러그인 경로와 skills CLI를 연결하는 얇은 계층으로 설계하는 것이 적합하다. 두 방식의 설치 단위와 이름을 같은 것으로 취급하지 않는다. 현재 자체 설치기는 이름에 `aiwf-`를 붙이지만 standalone skills 설치는 원래 이름을 사용하므로 스택 간 `implement` 같은 이름과 다른 설치 관리자의 파일을 함께 확인해야 한다.

설치 대상이 Claude라는 선택, Claude 위임 스킬을 설치한다는 선택, 실제 교차 CLI 실행 동의는 각각 별개다. 기존 위임의 `--cross-cli`·작업 범위 계약을 유지한다. 설치만으로 인증·모델 설정·별도 에이전트 실행을 시작하지 않는다.

## 공식 설치 방식과의 연결

2026-10-05 공식 문서 확인 결과다. 설치된 CLI 버전별 실동작을 새로 검증한 결과는 아니다.

| 방식 | 문서에서 확인한 계약 | AIWF 설계에 반영할 점 |
| --- | --- | --- |
| skills CLI | `npx skills add <source> --skill <a> <b> --agent codex claude-code --yes`처럼 여러 스킬·호스트를 선택할 수 있다. 프로젝트 범위가 기본이며 `--global`, `--copy`를 제공한다. | 선택 스킬 배포의 공식 경로를 활용한다. `--all`은 모든 호스트까지 선택하므로 AIWF 추천 구성의 의미로 사용하지 않는다. [공식 README](https://github.com/vercel-labs/skills#options) |
| Claude 네이티브 플러그인 | `claude plugin marketplace add <source>`와 `claude plugin install <plugin>@<marketplace> --scope project`를 제공한다. | AIWF가 선택 목록을 계산하고 플러그인별 실행 결과를 모을 수 있다. 파일 복사로 네이티브 설치를 흉내 내지 않는다. [공식 명령 참조](https://code.claude.com/docs/en/plugins/cli-reference) |
| Codex 네이티브 플러그인 | `codex plugin marketplace add <source>`와 `/plugins`·앱의 플러그인 설치 흐름을 문서화한다. `.claude-plugin/marketplace.json`도 호환 대상으로 설명한다. | 확인한 문서만으로 비대화형 `codex plugin install`을 지원한다고 단정할 수 없다. 초기 자동 설치는 검증한 skills 경로를 사용하고, 네이티브 모드는 지원되는 설치 UI와 연결하는 범위를 정확히 표시한다. [공식 패키징 문서](https://developers.openai.com/plugins/build/plugins), [플러그인 안내](https://learn.chatgpt.com/docs/plugins) |

skills CLI의 목록·갱신과 네이티브 플러그인의 목록·갱신은 서로 다른 설치 관리 작업이다. 플러그인은 스킬 외에 에이전트·훅·연결 설정도 포함할 수 있으므로, skills 설치 성공을 전체 플러그인 설치 성공으로 표시하지 않는다. [skills CLI](https://www.skills.sh/docs/cli), [Claude 플러그인 참조](https://code.claude.com/docs/en/plugins-reference), [Codex 플러그인 안내](https://learn.chatgpt.com/docs/plugins).

사용자 범위 경로는 README 표만 보고 추정하지 않고 `skills@1.7.0`의 배포 소스와 실제 설치 결과를 기준으로 정했다. 회귀 검사의 격리된 경로·backend 대역과 독립 리뷰의 임시 사용자 환경에서 Codex·Claude 사용자 범위 설치를 확인했다. 실제 사용자 전역 스킬을 변경하거나 Codex/Claude의 런타임 인식을 확인한 기록은 아니다. `CLAUDE_CONFIG_DIR`가 설치 때와 달라지면 `configuration_changed`로 현재 경로 차이를 표시하며 기존 파일이 삭제됐다는 뜻은 아니다. [고정 버전의 경로 구현](https://github.com/vercel-labs/skills/blob/7407f3893ad4dceab546ac002c3ef806e4000c73/src/installer.ts#L118-L164).

## 문서와 후속 검증

원문 스킬·플러그인 README가 바뀌면 한글 검토본과 manifest를 같은 변경에서 갱신한다. 이번 CLI 작업은 실행 스킬 원문과 플러그인 README를 변경하지 않았으며 루트 README 원문·한글본, 작업 지침과 방향 문서를 함께 갱신했다. 번역 해시와 휴먼 검토 상태는 변경하지 않는다. 번역 파일은 설치용 스킬로 만들지 않는다.

구현 시 필요한 검증은 최초 설치, 동일 구성 반복, 나중에 스택·위임 추가, 로컬 수정 보존, 두 설치 관리자 간 충돌, 복수 호스트별 인식, 부분 실패와 재시도다. 한글 문서 동기화도 완료 조건이다. 실제 생산성 효과는 설치 완료까지의 단계 수·실패율과 구성 변경 성공 여부로 평가한다.

휴먼 리뷰 항목은 설치 안내·추천 구성의 적절성, 실제 호스트에서의 스킬 선택, 개별 스킬 선택과 갱신·제거의 후속 범위다. 사용자 결정과 코드 검증을 문서의 실제 휴먼 리뷰 완료로 기록하지 않는다.

설치 개선 전 검토에서는 한글 문서 80개와 기존 설치 회귀 검사 16개를 확인했다. 후속 구현에서는 새 CLI·공유 리소스 준비·설치 상태와 충돌·부분 실패·실제 skills backend를 반복 가능한 회귀 검사로 추가했다. 임시 프로젝트는 검사 종료 후 삭제한다. 최종 검증 결과와 npm 전역 설치 경로의 확인은 아래에 기록한다. 휴먼 리뷰 기록은 0건이고 관리 대상 문서는 모두 검토 대기 상태다.

## 구현 검증 결과

환경: macOS, Node.js `22.23.1`, npm `10.9.8`.

- 전체 회귀 검사: `npm test` **112개 통과**, 실패 0. 기본 설치·동일 구성 유지·스택 및 다른 호스트 추가·사용자 범위 경로·로컬 수정 보존·심볼릭 링크와 lockfile 보호·부분 실패 재시도·실제 skills backend·npm bin 링크를 포함한다.
- `npm run docs:check`: 관리 대상 한글 문서 80개 정합성 통과. `npm run check:deps`, `npm run validate:spec-plugin`, Python 검사기 자체 검사 3종과 명세 예제 검사 통과. 기존 스킬 원문·추적 자료의 보존을 확인했다.
- `npm pack`으로 `aiwf-0.5.0.tgz`를 만들고 격리된 prefix에 `npm install --global`로 설치했다. 저장소와 다른 소비 프로젝트에서 npm이 만든 `aiwf` 실행 파일의 버전 `0.5.0`과 기존 `aiwf-spec --help`를 확인했다.
- 패키지에 포함된 skills `1.7.0`을 사용해 core/spec + Electron + 위임 2종을 Codex·Claude 프로젝트 경로에 **각 17개, 총 34개** 실제 설치했다. dry-run은 34개 목적지를 표시했고 같은 명령의 재실행은 34개를 유지했으며 `aiwf status`는 정상으로 확인했다.
- 격리된 prefix·소비 프로젝트·npm 캐시·tarball과 준비용 임시 폴더는 모두 정리했다. 일회성 검증 코드는 저장소에 추가하지 않았다. `.aiwf/skill-sources/`는 소비 프로젝트 설치 계약의 일부이며 일회성 fixture가 아니다.
- 독립 코드 리뷰에서 설치를 막는 결함은 없었으며, 다른 볼륨의 임시 경로에서 소스를 옮기는 위험을 발견해 준비 폴더를 정식 소스와 같은 부모에 두도록 수정했다. Markdown 심볼릭 링크를 따라 쓰지 않도록 거부하고 회귀 검사로 외부 원문 보존을 확인했다. 리뷰의 `APPROVE`는 AI 코드 리뷰 의견이며 휴먼 리뷰나 배포 승인이 아니다.

npm 레지스트리 게시, 사용자 실제 전역 스킬 변경, Windows 환경, 호스트의 스킬 자동 선택·모델 실행과 실제 휴먼 리뷰는 이번 검증에 포함하지 않았다. 배포된 `0.4.0`이 이 설치 기능을 제공한다고 안내하지 않는다.
