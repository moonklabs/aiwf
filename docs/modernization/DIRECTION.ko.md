# AIWF 개선 방향

작성: 2026-10-02. 안내 문구 정리: 2026-10-05.

## 결정

AIWF를 **유스케이스 명세를 실제 구현과 검증으로 연결하는 개발 워크플로우**로 전환한다. 개발자는 기존 Claude Code/Codex와 프로젝트의 기술 스택을 사용한다. 명세는 Git에 남고, Sprintable은 향후 팀의 작업·검토·승인을 연결한다.

예를 들어 “직원이 지출 내역을 제출한다”는 목표를 먼저 명세한다. 정상 제출, 금액 오류, 저장 실패 시 보장, 업무 규칙을 정의하고 각각의 검증 방법을 작성한다. 에이전트는 그 범위만 구현하고 실제 테스트 로그를 남긴다. 검토자는 어떤 명세 버전으로 무엇을 구현했고 무엇을 아직 확인하지 못했는지 한 묶음으로 읽는다. 다음 변경도 같은 명세를 수정하는 데서 시작한다.

## 방법론 구성

방법론 core는 `plugins/aiwf-core`의 스킬 7개, 문서 형식, 참조 템플릿과 Python 검사기로 구성한다. 기술 스택 5종은 `plugins/aiwf-vaadin-jooq`, `plugins/aiwf-angular-jpa`, `plugins/aiwf-blazor-dotnet`, `plugins/aiwf-nestjs-nextjs`, `plugins/aiwf-electron-react`에서 구현·테스트 스킬 30개를 제공한다.

- 비전 → 요구사항 → 용어집/엔티티 → 유스케이스 → 테스트 정의.
- `FR-001`, `UC-001`, `TC-001`로 연결하고 `UC-001 BR-001`처럼 업무 규칙의 소속을 표시한다.
- 기존 시스템은 reverse-engineer로 실제 동작부터 조사한다.
- 명세를 일회성 프롬프트로 버리지 않고 제품과 함께 유지한다.
- 문서의 구조·참조 검사와 사람이 판단하는 의미 검토를 구분한다.

스킬은 에이전트 지침이며 실행 강제 장치가 아니다. 추적표는 문서 간 연결을 계산할 뿐 구현이나 테스트 실행을 증명하지 않는다. 상태 변경이나 파일 변경만으로 테스트 성공을 판단하지 않고 실제 실행 로그를 별도로 확인한다.

## 책임 경계

| 구성 | 책임 | 이번 상태 |
|---|---|---|
| 명세 `docs/` | 원하는 동작과 검증 정의, 안정적인 ID | 표준 명세 형식 사용 |
| `aiwf-core` 플러그인 | 요구사항·엔티티·유스케이스·명세 검토 지침 (필수 core) | 방법론 스킬 7개 |
| `aiwf-spec` 플러그인 | AIWF `workflow`, `sync-docs`, host 중립 작업 추적·증거 경계 | 자체 스킬 2개 |
| stack 플러그인 `aiwf-<stack>` | 스택별 마이그레이션·구현·테스트 지침 | 구현·테스트 스킬 5종 |
| `aiwf` CLI | 호스트·스킬 구성 선택, 공식 skills CLI 설치, 반복·추가 설치와 상태 확인 | `0.5.0` 작업 트리 구현; npm 배포 대기 |
| `aiwf-spec` CLI | 초기화, 명세 버전 고정, 변경 감지, 검증 로그 묶기 | 로컬 구현 |
| 현재 코딩 에이전트 | 코드 수정, 프로젝트 테스트 실행, 결과 보고 | 기존 도구 사용; 별도 모델 런타임 없음 |
| Sprintable 어댑터 | 작업과 명세 버전 연결, 문서/증거 업로드 | 다음 단계 설계 |
| 검토자/승인자 | 검토·업무 수용·승인 | 자동 통과로 대체하지 않음 |

완료, 테스트 통과, 업무 수용, 승인, 병합, 배포는 서로 다른 사실이다. SHA256은 파일이 같은지 알려주며 내용이 옳은지는 알려주지 않는다. 이번 CLI의 packet은 에이전트가 보고한 결과와 로그를 기록하고 `awaiting_review`로 남긴다.

## 레거시 정리

2026-10-03 사용자 결정에 따라 예전 설치기·페르소나·언어/스프린트/YOLO 런타임, 중복 스킬·명령·규칙, 레거시 플러그인과 문서를 제거했다. 당시 정리 범위는 core/workflow/stack 플러그인 6개와 의존성 없는 명세 CLI였다. 이후 선택 위임 애드온 2개와 Electron/React 스택 1개를 더한 현재 구성은 총 9개이며 위임 설치·실행은 선택 사항이다. 과거 기록은 Git 이력과 changelog에 남긴다. 실제 제품 앱의 파일럿은 별도 검증이 필요하다.

## 진행 순서

2026-10-05 사용자 결정에 따라 CLI의 첫 역할은 **프로젝트에 맞는 플러그인·스킬 구성의 일괄 설치와 안전한 구성 변경**이다. 기본 사용 흐름은 `npm i -g aiwf` → `aiwf install`로 정하고, 실제 스킬 배치는 고정한 공식 skills CLI를 활용한다. CLI 전역 설치와 스킬 설치 범위는 별개다. [설치 중심 역할과 구현 검토](CLI-INSTALLATION-REVIEW.ko.md)에 새 `aiwf` 진입점·호스트 선택·반복 및 추가 설치·상태 조회와 남은 갱신/제거·프로필 범위를 정리했다. `aiwf-spec`는 유지한다. 작업 트리 `0.5.0`은 구현 상태이며 npm 배포·휴먼 리뷰는 대기 상태다.

2026-10-03 후속 [CLI 생산성 분석](CLI-PRODUCTIVITY.ko.md)은 현재 도구로 실제 UC 파일럿을 먼저 수행하고, 관찰된 반복 절차를 읽기 전용 검사 통합과 UC/BR/TC에 연결된 선택 실행·버전 기록으로 줄이도록 권고한다. 원문·한글본 갱신은 모든 작업의 품질 조건이며 문서 검토 보고서와 CI는 이를 지원하는 유지보수 개선이다. 이 제안들은 기존 CLI에 추가된 기능이 아니다. 파일럿의 시간·검토 누락 측정으로 후속 자동화 범위를 정한다.

1. **로컬 기반:** `aiwf-core`/`aiwf-spec` 분리와 4개 stack 이식, 완전한 한국어 예제, 구조 검사, 명세 pin/change check, 검증 로그 packet, Claude/Codex 설치 경로. 이번 작업 범위다.
2. **실제 기능 파일럿:** 작은 실제 저장소에서 UC 하나를 선택한다. 정상 흐름과 실패 흐름을 구현하고 실제 앱 동작을 확인한다. 문서 작성부터 실행 결과까지 걸린 시간, 검토 횟수, 명세 대비 누락을 기록한다. 이 결과로 명세 양과 workflow를 조정한다.
3. **Sprintable 연결:** 프로젝트/작업을 명시적으로 연결하고, packet을 문서로 등록하고, report evidence와 필요 시 승인 게이트를 만든다. 수정된 명세를 기존 승인으로 통과시키지 않는 버전 계약을 검증한다.
4. **반복 실행:** 파일럿 이후 CI/에이전트 작업 큐·중단/재개·재시도·동시 작업 격리를 추가한다. 저장소 변경, 실패한 테스트, 승인 대기가 있는 경우 자동으로 병합하지 않는다. 반복 실행은 아직 구현되지 않았다.


방법론 core 7개는 `plugins/aiwf-core`에, AIWF `workflow`는 `plugins/aiwf-spec`에 분리했다. 이전에는 core 7개를 `aiwf-spec`에 넣어 방법론 core와 AIWF 래퍼가 한 플러그인에 섞였는데, 원본 소스는 그대로 두고 위치만 옮겨 바로잡았다. 새 설치 CLI는 core와 `workflow`, `sync-docs`를 추천하고 `--core-only`·선택 스택·위임을 제공한다. 기존 checkout 복사 스크립트는 core/spec와 스택 하나를 설치하며 기존 목적지를 거부하는 계약을 유지한다. 두 경로 모두 네이티브 Codex 에이전트를 등록하거나 MCP 서버를 자동 구성하는 기능은 아니다. 어느 스택을 실제 파일럿에 쓸지는 대상 저장소 규칙에 맞춰 선정한다.

## 이번 범위의 검증과 남은 것

검증 내역은 [VALIDATION.md](VALIDATION.md)에 기록한다. 구조 검사 통과와 로컬 CLI 테스트는 실제 에이전트가 애플리케이션을 성공적으로 개발했다는 증거가 아니다. Claude/Codex의 실제 스킬 자동 선택, 실제 앱 파일럿, Sprintable 운영 연동, 자동 승인 무효화, 무인 반복 실행은 후속 검증 범위다.
